# Ретроспектива — вход по «волшебной ссылке» (passwordless)

**Дата:** 2026-06-28

## Задача
Артём пожаловался на трение регистрации/пароля, предложил соцвходы (VK/Google/Apple).
По итогу обсуждения выбрали полный passwordless (вход + регистрация по ссылке из письма),
без соцсетей.

## Как решал
1. Возразил против соцвходов аргументами: приватность покер-аудитории (правило 5),
   связность Google/Apple из РФ через релей, цена Apple, дубли аккаунтов. Предложил
   magic link на готовой почтовой инфраструктуре. Артём согласился.
2. Через Explore-агента поднял всю механику auth (сброс пароля — почти готовый каркас).
3. Уточнил объём через вопрос (полный passwordless vs только вход vs оба) — выбрал полный.
4. План в `plans/`, спросил разрешение на миграцию БД (правило проекта), получил «делай».
5. Реализовал по фазам: схема → конфиг → токен/письмо/cookie → actions → GET-роут → UI → тесты.

## Решил
**Да** — функция работает целиком, тесты (12 новых + 58 auth) и build зелёные. НЕ задеплоено.

## Что было неочевидно / что лучше в следующий раз
- **Дрейф миграций** на dev и test: `migrate dev` хотел reset (потеря данных). Применил
  одну таблицу точечно через `db execute` идемпотентным SQL — приём уже заведён в проекте
  (миграция сброса пароля). Тестовую базу пришлось накатывать отдельно.
- **Cookie в GET-роуте:** Set-Cookie из next/headers ненадёжно переживает
  NextResponse.redirect — вынес дескрипторы cookie (`buildSessionCookie`/
  `buildPendingRegistrationCookie`) и ставлю прямо на ответ. Работает в тестах.
- **Всплывший дефект:** passwordless-аккаунты не закрываются и не меняют пароль через
  «Аккаунт» (формы требуют пароль). Не стал чинить молча (потоки про данные/доступ) —
  зафиксировал в журнале и плане, вынес Артёму на решение.

## Как стало
Появился третий способ входа рядом с паролем. Аккаунт без пароля — штатный
(`passwordHash` NULL уже поддерживался схемой). Дальше: решение Артёма по хвосту
(закрытие/смена пароля беспарольных), копирайт письма, деплой + ручная миграция на прод.
