# Ретроспектива — security-review деплоя и фиксы

**Дата:** 2026-06-16, 16:45

## Задача

Свежий security-review прод-кода (сайт уже публичен, живые email игроков, никнеймы в HH) по чек-листу из 8 пунктов: ввод/XSS/SQL, секреты, права доступа, логи, ошибки наружу, двойное списание, утечки во фронт, загрузка файлов. Затем — починить все находки так, чтобы всё работало.

## Как решал

Прочитал реальный код по каждой точке входа, а не по памяти: auth (сессия/пароль/экшены/ownership), все API-роуты, server actions, парсер, LLM-адаптер, очередь, рендер статуса, next.config. Проверял вещи про вход/деньги/ПДн дважды (страницы турнира и раздачи — отдельно от API).

Картина: после hardening-прохода 2026-06-15 код крепкий. IDOR закрыт и на API, и на страницах; SQL только через Prisma (raw — через `Prisma.join`); XSS нет (React экранирует, `dangerouslySetInnerHTML` отсутствует); секретов в гите нет; ключ LLM и промпты только на сервере; файл не сохраняется на диск, лимит 5 МБ; парсер линейный (без ReDoS); логи без ПДн.

Реальные находки и фиксы:
1. **Перебор пароля / credential stuffing** (главное) — на `loginAction`/`registerAction` не было rate limit, хотя раздел 2 архитектуры его прямо предписывал. Сделал in-memory счётчик с фиксированным окном (`features/auth/rate-limit.ts`), пороги в конфиге (`config/auth.ts`, env-override), IP — за Cloudflare-туннелем (`cf-connecting-ip`/`x-forwarded-for`). Вход блокируется по email и по IP, сброс по email при успехе; регистрация лимитирована по IP (это же тормозит «прозвон» занятых почт).
2. **Текст ошибки задачи наружу** — `task.error` убран из `/api/status` и с экрана статуса, пользователю общий ярлык, полный текст в БД.
3. **Заголовки безопасности** — добавил в `next.config.ts` (CSP без ломающих Next директив, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy, HSTS).

Лимитер выключил в тестовой среде (все тесты делят процесс и общий IP-фолбэк), а чистый счётчик покрыл отдельным тестом с управляемым временем.

## Решил: да

Все находки из объёма закрыты. 117/117 тестов зелёные, `next build` + линтер + типы чисто.

## Что было бы лучше

- IP-определение проверено только сборкой/логикой, не живым curl к прод-туннелю — стоит подтвердить `cf-connecting-ip` после деплоя.
- Счётчик в памяти процесса: при переходе на несколько инстансов нужен общий store (Redis/PG) — тот же долг, что у in-process блокировки воркера.

## Как стало

Перебор пароля по живым аккаунтам теперь упирается в блокировку; внутренние ошибки не светятся пользователю; ответы отдаются с защитными заголовками. Решение — в журнале `architecture/07-безопасность.md` (2026-06-16).

## Осталось на потом (вне объёма, требует решения)

- Полное устранение перечисления email через регистрацию — нужна email-верификация (адаптер почты Unisender Go, отдельная фича).
- Сброс пароля по одноразовой ссылке (тоже почта).
- Часовые лимиты на загрузку файлов и сообщения чата (раздел 2 архитектуры) — защита кошелька, актуальна к моменту, когда заработает платный ключ LLM.
- Журналирование неудачных входов с временем (раздел 2) — когда появится аудит-лог.
