# Ретро: воркеры карточки — сохранение всех раздач + LLM-разбор + CARD_READY

**Дата:** 2026-06-13 20:22
**Длительность:** продолжение сессии (после компакции контекста)
**План:** `plans/2026-06-13-воркеры-карточки-llm-разбор.md`

## 1. Задача

При разборе турнира воркеры должны: запустить `selectHandsForCard`, сохранить все ~70 раздач в `hands` с флагом `selected_for_card`, для отобранных ~10 сгенерировать LLM-разбор через адаптер, после чего перевести турнир в статус `CARD_READY`.

## 2. Как решал

1. `PARSE_TOURNAMENT` переписан: payload теперь несёт весь `ParsedTournament` (включая `hands[]`), шаг идемпотентно сохраняет все раздачи через `createMany` (id генерируются заранее, нужны для постановки следующих задач), помечает `selectHandsForCard`-результат флагом `selected_for_card`, ставит по одной задаче `GENERATE_HAND_ANALYSIS {handId}` на каждую отобранную.
2. Добавлен LLM-адаптер за портом (`infrastructure/adapters/llm/{types,anthropic,fake,index}.ts`, `config/llm.ts` с `ANTHROPIC_MODEL`): `fakeLlmAdapter` детерминированно работает без сети (используется в деве/тестах, т.к. `ANTHROPIC_API_KEY` пуст), `anthropicLlmAdapter` — реальный вызов с валидацией JSON по `importanceLevel`. Промпт `config/prompts/hand-analysis.ts` содержит обязательные строки правила 1 («не вычисляй метрики», «не уверен — задай вопрос»).
3. Новый шаг `GENERATE_HAND_ANALYSIS`: идемпотентен (`hand.analysis !== null` → пропуск платного вызова), для `CRITICAL` создаёт `Dialogue {question, state: QUESTION_ASKED}` без вердикта (правило 2 — `draftVerdict` остаётся внутри `analysis`, в `dialogues.verdict` не попадает до ответа игрока). После сохранения проверяет, обработаны ли все отобранные раздачи турнира (успешно или `POISONED`) — если да, переводит турнир в `CARD_READY`.
4. Написаны тесты: `__tests__/queue/parse-tournament.test.ts` (12 раздач → 10 отобранных по формуле 2+5+3, идемпотентность), `__tests__/queue/generate-hand-analysis.test.ts` (7 кейсов — сохранение анализа, диалог для CRITICAL, условие CARD_READY, POISONED не блокирует, идемпотентность, ошибка без метрик турнира). Обновлён приёмочный тест `upload-tournament.test.ts` — полный цикл от загрузки файла до `CARD_READY` на фикстуре с 6 раздачами (2 CRITICAL → 2 диалога).
5. `npm test`: 7/7 файлов, 39/39 тестов. `tsc --noEmit` — чисто.

## 4. Что можно было лучше

- **Тестовая БД разошлась с миграциями** — `trener_test` имела таблицу `tasks`/enum `TaskStatus` уже созданными, но без записи в `_prisma_migrations` (та же природа проблемы, что и в прошлой сессии с dev-базой, см. `project_db_setup.md`). Починилось `prisma migrate resolve --applied` + `migrate deploy`. Если это повторится в третий раз — стоит один раз разобраться в первопричине рассинхрона `_prisma_migrations`, а не лечить симптом каждый раз.
- **Рабочая директория для `tsc`/`vitest` в этом Git Bash окружении** — команды нужно запускать из `trener/` (алиасы `@/...` резолвятся относительно `trener/vitest.config.ts`), и использовать `./node_modules/.bin/tsc` вместо `npx tsc` (иначе npx ставит левый пакет `tsc@2.0.4`). Стоит запомнить на будущее, чтобы не тратить время на диагностику.
- **Найден и исправлен попутный баг** в `claimTask` (`infrastructure/queue/worker.ts`): `run_after AT TIME ZONE 'UTC' <= NOW()` без приведения `NOW()` к `timestamp(3)` давал ~1.5% промахов для свежепоставленных задач из-за округления при записи `run_after` — причина редкой нестабильности (1 тест из 39 падал через раз). Исправлено `NOW()::timestamp(3)`, проверено стресс-тестом (0/500). Решил, что это в рамках задачи: маленькое точечное изменение в коде очереди, над которым я и так работал, напрямую влияет на надёжность написанных в этой сессии тестов.
