Артём попросил 2026-06-26 «звоночек», когда пора улучшать сервер при росте аудитории.

**Как устроено сейчас:** один ПОСЛЕДОВАТЕЛЬНЫЙ воркер (`runWorkerOnce` в цикле, дёргается кроном раз в 15с — [[project_queue_latency]]). Внутренний замок `isRunning` не даёт двум прогонам идти разом → тяжёлая работа (вызов Claude) всегда по ОДНОЙ задаче. Пропускная ~2–6 задач/мин. 100 одновременных запросов → НЕ падение, а длинная очередь (последний ждёт минуты). Узкие места под реальным пиком: пул соединений Prisma к БД (по умолчанию ~5, не настроен явно в `infrastructure/db/client.ts`) и нагрузка от опроса страниц (каждый poll = пара чтений БД; на 1с/100 страниц ощутимо).

**Звоночки по нарастанию (рычаг → когда включать):**
1. **Параллельный воркер** (дёшево, БЕЗ нового железа — брать несколько задач разом). Триггер: очередь регулярно копится — PENDING висит > ~2–3 мин в обычный день, или жалобы на ожидание. `/api/health` УЖЕ проверяет «очередь не встала» (PENDING старше порога, `config/health.ts`) — это готовая основа звоночка. Шаг: вынести счётчик длины очереди в утренний дайджест.
2. **Больше сервер / Managed PostgreSQL + поднять пул соединений.** Триггер: ошибки про соединения к БД (P2024 pool timeout), или CPU/RAM на VM стабильно высокие. Health/UptimeRobot это пока НЕ меряют — добавить базовую нагрузку (CPU/RAM/кол-во соединений) в дайджест.
3. **Несколько инстансов приложения + PostgreSQL advisory lock** (код это предвидит — комментарий в `app/api/cron/run-tasks/route.ts`). Далеко.

**Практика:** пока одновременных пользователей единицы — не трогать ничего. Первый шаг при росте — параллельная обработка (рычаг №1), снимает очередь без апгрейда железа. Связано: [[project_queue_latency]], [[project_health_monitoring]].

## ✅ СДЕЛАНО (2026-07-31): звоночки подключены — сторож нагрузки на VM
После инцидента с падением nginx на релее (тот же день, [[project_deploy_status]]) Артём спросил и про сценарий «набежала 1000 человек разом». Поставлен второй, отдельный от down-сторожа скрипт — **на самой VM** (не на релее, т.к. ему нужен доступ к БД и метрикам сервера), шлёт в Telegram тот же канал через релей-прокси (`TELEGRAM_BASE_URL`+`x-proxy-secret`, тот же путь, что у daily-digest).

Файлы на VM (НЕ в git):
- `/usr/local/bin/load-watchdog.sh` — 4 проверки, алерт только на ПЕРЕХОДЕ через порог (не спамит, пока состояние держится):
  1. **Очередь**: `PENDING`-задач в `tasks` старше 3 минут > 5 → «наплыв, воркер не успевает».
  2. **Соединения к БД**: `pg_stat_activity` > 60% от `max_connections` → «приближаемся к пределу» (это и есть причина инцидента 01.07, см. [[project_queue_latency]]).
  3. **CPU**: load average (1 мин) > 1.5×ядер (VM 2 ядра → порог 3.0).
  4. **Память**: доступно < 15% (VM всего ~2ГБ RAM).
- Состояния — `/home/trener-vm/.load-watchdog-state/*.state` (up/down по каждой проверке отдельно).
- Cron `*/5 * * * *` в crontab `trener-vm` (рядом с остальными cron, бэкап `crontab.bak.<ts>`), лог `/home/trener-vm/load-watchdog.log`.
- Проверено вживую: прогон вручную exit 0, все 4 показателя "ok" (сайт не под нагрузкой), тестовое сообщение по каналу VM→релей→Telegram дошло.

⚠️ Грабли при написании: функция вырезания кавычек из `.env.production` (`tr -d "\"\x27"`) по ошибке съедала цифры 2 и 7 из IP релея (внутри двойных кавычек bash НЕ разворачивает `\xHH`) — IP `92.60.75.87` превращался в `9.60.5.8`. Исправлено на `sed "s/[\"']//g"`. Если где-то ещё в скриптах есть похожая конструкция — проверить.

**Это НЕ автомасштабирование** — только раннее предупреждение в Telegram, чтобы Артём успел среагировать (например, включить рычаг №1 параллельного воркера или вручную поднять ресурсы VM) ДО того, как люди почувствуют тормоза, а не после жалоб.
