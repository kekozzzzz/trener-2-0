Артём попросил 2026-06-26 «звоночек», когда пора улучшать сервер при росте аудитории.

**Как устроено сейчас:** один ПОСЛЕДОВАТЕЛЬНЫЙ воркер (`runWorkerOnce` в цикле, дёргается кроном раз в 15с — [[project-queue-latency]]). Внутренний замок `isRunning` не даёт двум прогонам идти разом → тяжёлая работа (вызов Claude) всегда по ОДНОЙ задаче. Пропускная ~2–6 задач/мин. 100 одновременных запросов → НЕ падение, а длинная очередь (последний ждёт минуты). Узкие места под реальным пиком: пул соединений Prisma к БД (по умолчанию ~5, не настроен явно в `infrastructure/db/client.ts`) и нагрузка от опроса страниц (каждый poll = пара чтений БД; на 1с/100 страниц ощутимо).

**Звоночки по нарастанию (рычаг → когда включать):**
1. **Параллельный воркер** (дёшево, БЕЗ нового железа — брать несколько задач разом). Триггер: очередь регулярно копится — PENDING висит > ~2–3 мин в обычный день, или жалобы на ожидание. `/api/health` УЖЕ проверяет «очередь не встала» (PENDING старше порога, `config/health.ts`) — это готовая основа звоночка. Шаг: вынести счётчик длины очереди в утренний дайджест.
2. **Больше сервер / Managed PostgreSQL + поднять пул соединений.** Триггер: ошибки про соединения к БД (P2024 pool timeout), или CPU/RAM на VM стабильно высокие. Health/UptimeRobot это пока НЕ меряют — добавить базовую нагрузку (CPU/RAM/кол-во соединений) в дайджест.
3. **Несколько инстансов приложения + PostgreSQL advisory lock** (код это предвидит — комментарий в `app/api/cron/run-tasks/route.ts`). Далеко.

**Практика:** пока одновременных пользователей единицы — не трогать ничего. Первый шаг при росте — параллельная обработка (рычаг №1), снимает очередь без апгрейда железа. Связано: [[project-queue-latency]], [[project-health-monitoring]].
