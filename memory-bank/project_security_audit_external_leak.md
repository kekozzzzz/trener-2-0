Полный аудит «может ли посторонний снаружи что-то украсть с сайта» — проведён 2026-08-16/17, критичных дыр не найдено.

**Проверено кодом (Explore-агент) и подтверждено:**
- next.config.ts — security-заголовки (CSP, X-Frame-Options, HSTS и т.д.) на всех роутах; source maps в проде выключены (дефолт)
- Хранилище HH-файлов (infrastructure/adapters/storage/) — в коде вообще нет функции чтения/скачивания наружу, только `put`. ACL при загрузке не выставляется явно
- Все API-роуты (app/api/**), отдающие данные, защищены `authorizeHand`/`requireSession`/секретными токенами для cron и вебхуков
- Ключи/секреты не попадают в клиентский бандл (единственный NEXT_PUBLIC_ — id счётчика Метрики), не встречаются в истории git
- Ошибки наружу не показывают внутренности БД/стек — только общие коды
- Админка (app/admin) — чужому отдаёт 404, не 403, не подсказывает о своём существовании

**Проверено вручную в консоли Yandex Cloud (Артём, скриншоты 2026-08-17), бакет `whygrid-hh-store`:**
- Настройки → Основные → Доступ: «Чтение объектов», «Чтение списка объектов», «Чтение настроек» — везде «С авторизацией» (не «Для всех»)
- Безопасность → Права доступа: только владелец (Артём) и сервисный аккаунт `whygrid-storage` (роль storage.editor) — ни одной публичной/анонимной записи

**Архитектурный риск на будущее (не дыра, но не проверить одним взглядом):** middleware.ts не делает централизованную авторизацию — каждая страница/роут/action сама вызывает проверку доступа. Работает исправно сейчас, но при добавлении НОВОЙ функции с чужими данными легко забыть добавить проверку — нет одного общего «рубильника». При ревью новых фич с данными пользователей — сверять это явно.

**Не проверено (не входит в код, требует ручной сверки при следующем аудите):** вкладка «Политика доступа» бакета (JSON policy) — отдельный документ, который теоретически может переопределить обычные ACL-настройки. В этот раз не смотрели, стоит глянуть при следующей проверке.
