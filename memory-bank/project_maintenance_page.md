Если сайт падает (крашнулся Node-процесс ИЛИ легла вся ВМ), посетитель видит страницу «Идут технические работы» вместо голой ошибки nginx или обрыва соединения. Механизм — чистый nginx, без Node, поэтому работает даже если приложение полностью не отвечает.

**Файл страницы:** `design/maintenance.html` в репозитории (не деплоится автоматически — это просто исходник для правок, копия лежит на серверах отдельно, вручную).

**Где реально висит (на серверах, НЕ в git — как и весь nginx-конфиг):**
- ВМ (81.26.186.177): `/var/www/whygrid-maintenance/maintenance.html`, конфиг `/etc/nginx/sites-available/whygrid` — в блоке `listen 443` добавлены `error_page 502 503 504 /maintenance.html;`, `location = /maintenance.html { root ...; internal; }`, `proxy_intercept_errors on;` в `location /`. Ловит случай «упал сам Node-процесс, ВМ жива».
- Релей (92.60.75.87): та же тройка директив в `/etc/nginx/sites-available/whygrid` (тот же путь, отдельная копия файла страницы). Ловит случай «вся ВМ недоступна» (как инцидент 20.08, [[project_vm_hang_incident_20260820]]) — тогда сработает уже этот, внешний, слой.

**Проверено вживую 2026-08-21:** на ВМ — временный тестовый location с `return 502;` реально отдал страницу техработ с кодом 502 (не просто текст, настоящий HTTP-статус). Прямой доступ к `/maintenance.html` заблокирован (`internal`, 404) на обоих слоях. На релее подмена апстрима на несуществующий IP (`192.0.2.1`, TEST-NET — пакеты молча теряются, честная имитация зависшей ВМ, а не мгновенный «отказано») дала 504 → страницу техработ через 7 секунд (после добавленного `proxy_connect_timeout 7s`, см. ниже). ⚠️ Тестируя fault-injection через `sed`+`reload`, ловил ложные «всё ок» на первом запросе сразу после reload — старые nginx-воркеры ещё живут пару секунд и могут принять новое соединение со старым конфигом; фикс — `sleep 2` после `systemctl reload` перед проверкой. Бэкапы оригинальных конфигов лежат рядом (`whygrid.bak.<timestamp>`) на обоих серверах.

**Правка 2026-08-21 (в тот же день, по вопросу Артёма «а с телефона иногда ничего не видел»):** без явного `proxy_connect_timeout` nginx-дефолт — 60 секунд ожидания перед тем, как показать страницу техработ при зависшей (не отвечающей на TCP, но и не отказывающей) ВМ — сценарий ровно как [[project_vm_hang_incident_20260820]]. За минуту телефон/браузер скорее покажет свою нативную ошибку раньше, чем дождётся нашей страницы. На релее (`/etc/nginx/sites-available/whygrid`, `location /`) добавлен `proxy_connect_timeout 7s;` — подтверждено замером: 7.04с до 504→страницы техработ. На ВМ (проксирование на `127.0.0.1:3000`) не трогал — локальный коннект отказывает мгновенно, реального риска долгого ожидания там нет.

**Что этой правкой НЕ закрыто (сознательно, отдельный риск):** полный обрыв СЕТИ у самого релея (как [[project_relay_nightly_outage]], 12-13.08, ~1.5ч дважды) — если пакеты физически не доходят до релея, никакая nginx-страница ответить не может, это единая точка отказа, второй релей отложен до первых пользователей. Артём подтвердил: скорее всего именно эти два инцидента (12-13.08 обрыв сети, 19-20.08 зависание ВМ) он и видел с телефона — оба случились ДО того, как эта страница вообще появилась.

Дизайн — по `design/design-system.md`: тёмный фон, один акцент лайм, шрифты с системным фолбэком (без внешних Google Fonts — страница должна рендериться даже если внешние подключения по какой-то причине недоступны), контакт `support@whygrid.app`.

**Полная картина по слоям ошибок (проверено 2026-08-21, вся нижняя часть уже была в проде до сегодня):**
- Сайт целиком не отвечает (Node упал / вся ВМ легла) → nginx-страница техработ (эта заметка, сделано сегодня).
- Упал сам корневой layout → `trener/app/global-error.tsx` (инлайн-стили, не зависит от Tailwind/globals.css).
- Упал рендер конкретной страницы → `trener/app/error.tsx` (фирменный стиль, «Попробовать снова»/«На главную»).
- Несуществующий адрес → `trener/app/not-found.tsx` (фирменная 404).
