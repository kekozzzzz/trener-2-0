`IntersectionObserver` с узким `rootMargin` (полоса ~80px) для отслеживания «элемент проезжает через тонкую зону при скролле» — плохой выбор. Браузер не гарантирует своевременную доставку колбэков для такой узкой зоны при обычной скорости скролла (не только при быстром флике).

**Why:** обнаружено 18.08.2026 на [[project_scroll_highlight_feature]] — Артём поймал баг и на телефоне, и на компьютере одинаково («проходит линию, и всё — выше линии уже не работает»), не Safari-специфика. Полный прогон скролла по странице с проверкой класса на каждом шаге показал: часть блоков вообще не получала класс «подсвечен» (колбэк не успел долететь до того, как элемент уже покинул зону), другой блок «залип» подсвеченным на 2760px скролла вместо своих честных 715px высоты (колбэк «покинул зону» пришёл с огромным опозданием).

**How to apply:** для любого эффекта «элемент проезжает через фиксированную узкую полосу/линию при скролле» — не использовать `IntersectionObserver`. Вместо этого: слушать `scroll`/`resize` с `passive:true`, throttle через `requestAnimationFrame`, и на каждом кадре напрямую сравнивать `el.getBoundingClientRect()` с границами зоны (`rect.bottom > zoneTop && rect.top < zoneBottom`). Дороже по производительности при большом числе элементов (десятки-сотни), но для разумного количества (< ~50) полностью детерминированно и не зависит от скорости скролла.

`IntersectionObserver` остаётся нормальным выбором для широких/грубых случаев (появление секции по скроллу, ленивая загрузка) — проблема именно в *узкой* зоне, где окно пересечения короткое по времени/расстоянию.
