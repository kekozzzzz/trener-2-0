Жалоба Артёма 2026-08-08: «когда на прод что-то выкатываешь, там постоянно ошибки приходят, типа перегрузка какая-то лютая».

**Причина найдена.** `/usr/local/bin/site-watchdog.sh` на релее дёргал `https://whygrid.app/api/health` раз в 2 минуты с таймаутом 10 с, и **ОДНОЙ** неудачной проверки хватало, чтобы улетело 🔴. А автодеплой идёт ~4 минуты (замер: 11:43:51→11:47:45): `npm install` → `prisma generate` → `next build` → рестарт pm2 на ВМ с 2 ГБ RAM, load подскакивает до 3+. Health-запрос не укладывался в таймаут — приходила тревога про ЗАНЯТОСТЬ, а не про падение. Сайт при этом жив: сборка идёт поверх работающего процесса.

**Починено (обе правки ТОЛЬКО на релее, в git их нет — [[project_remote_workspace]]):**
1. `site-watchdog.sh` — тревога после ДВУХ неудач подряд (`FAILS_TO_ALERT=2`, счётчик в `/var/run/whygrid-watchdog.fails`), таймаут 10→15 с, каждая неудача и отбой пишутся в `/var/log/whygrid-watchdog.log` (раньше сторож не оставлял следов вообще). Отбой ✅ шлётся только если тревога реально была. Бэкап: `site-watchdog.sh.bak-20260808`.
2. `autodeploy.sh` — `npm install` и `npm run build` завёрнуты в `nice -n 15 ionice -c3`: сборка уступает процессор живому приложению. Бэкап: `autodeploy.sh.bak-20260808`.

**Why:** от шума перестаёшь читать алерты вообще, а это опаснее самого шума. Настоящее падение по-прежнему заметно за ~2-4 минуты.

**Как проверить, что помогло:** после следующего выката `tail /var/log/whygrid-watchdog.log` на релее — если там `fail #1` без `ALERT sent`, значит блип был и его правильно проглотили.

⚠️Правило в CLAUDE.md «провал проверки сайта приходит в Telegram всегда» остаётся в силе — изменился только порог срабатывания, а не сам факт оповещения. [[project_deploy_procedure]] [[project_health_monitoring]] [[project_watchdog_bot]]

## Второй сторож — про нагрузку и память (09.08)

Артём прислал скриншот: «⚠️ Сервер сильно нагружен (load average 3.93 при 2 ядрах)» и «⚠️ Мало свободной памяти (доступно 12%)». Это НЕ site-watchdog, а `/usr/local/bin/load-watchdog.sh` **на самой ВМ** (cron `*/5`, лог `~/load-watchdog.log`). Он следит за четырьмя вещами: очередь разборов, соединения к БД, load average, свободная память.

Причина та же: тревога слалась при ПЕРВОМ же переходе через порог. Пороги — CPU `cores*1.5` (то есть 3.0 на двух ядрах) и память «доступно <15%». Сборка Next на 2 ГБ даёт ровно это на ~4 минуты. То есть на КАЖДОМ выкате прилетали две тревоги плюс потом два отбоя.

**Починено:** у `check()` появился 6-й аргумент `need` — сколько проб подряд должны быть выше порога. Для cpu, mem и queue поставлено 2 (то есть ~10 минут); для соединений к БД оставлено 1. Плюс `deploy_running()` (`pgrep -f "next build|prisma generate|npm install"`) — во время выката проверки cpu/mem пропускаются целиком. Каждая проба пишется в лог, раньше он был пуст всегда. Бэкап: `load-watchdog.sh.bak-20260809`.

⚠️Проверено на настоящей функции `check()`, извлечённой из боевого файла, с заглушкой вместо Telegram: разовый всплеск глотается, держащаяся перегрузка даёт тревогу со второй пробы, отбой приходит, во время выката тишина, счётчики разных метрик не путаются. На ЖИВОМ деплое ещё не проверено — смотреть `tail ~/load-watchdog.log` на ВМ после следующего выката.

⚠️Оба сторожа живут ТОЛЬКО на своих машинах и в git их нет: site-watchdog на релее, load-watchdog на ВМ.
