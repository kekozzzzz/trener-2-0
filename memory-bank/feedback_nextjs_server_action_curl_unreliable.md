При отладке 16.09 (магик-линк вход) несколько раз проверял `requestMagicLinkAction` через `curl -X POST https://whygrid.app/enter -d "email=..."`. HTTP-ответ был идентичен настоящему браузерному сабмиту (200, тот же размер тела) — выглядело как успех. На самом деле в БД (`magic_link_tokens`) НИ ОДНА такая curl-попытка не создала новую запись — код молча не доходил до отправки письма, хотя тот же самый код прекрасно отрабатывал и при реальном клике в браузере, и в изолированных диагностических скриптах. Причина не выяснена до конца (вероятно, специфика протокола Server Actions — Next-Action заголовок / формат тела, который реальный браузер шлёт иначе, чем простой form-urlencoded curl), но потратил на это лишний час, гоняясь за несуществующим багом в SMTP.

**Почему:** HTTP-код и размер тела ответа Server Action НЕ доказывают, что серверная функция реально выполнилась до конца — плохая обёртка (`{success:true}` для ЛЮБОГО исхода, намеренно, чтобы не палить перебором email) маскирует и рабочий, и «съеденный» путь одинаково.

**Как применять:** для проверки любого Next.js App Router Server Action (`<form action={fn}>`) в проде/деве — либо кликать реальным браузером (Playwright MCP или руками), либо проверять побочный эффект напрямую (новая строка в БД, файл на диске), а не полагаться на HTTP-статус curl-запроса как на доказательство. Если нужен автоматизированный тест без браузера — писать unit/integration-тест, вызывающий саму функцию действия напрямую (как уже делают тесты `__tests__/features/auth/*`), а не эмулировать HTTP снаружи.
