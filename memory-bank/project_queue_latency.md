Задержка ~30с на каждый шаг сократовского диалога была НЕ из-за LLM (короткий вопрос Claude генерит за 5–10с), а из-за ожидания в очереди: задача GENERATE_DIALOGUE_QUESTION лежала PENDING до следующего тика крона.

**Почему это важно (Артём, 2026-06-26):** «крутится 30+ секунд» для нового человека = «сайт тупит/плохо работает» → закрыл и не вернулся. Это причина чинить задержку, а не косметика. Держать ощущение быстрым — продуктовый приоритет, не тех-долг.

**Сделано 2026-06-26 (только на сервере, в репозитории НЕТ):** крон `/api/cron/run-tasks` в crontab `trener-vm` ускорен с раз-в-минуту до раз-в-15-секунд хитростью со сдвигом (4 строки `* * * * *`, паузы sleep 0/15/30/45). Безопасно: endpoint самоблокируется (isRunning → 429), задача лёгкая. Бэкап старого crontab — `/tmp/cron.bak.*` на VM. Средняя задержка пуска упала ~30с → ~7с. Подключение к VM — [[feedback-server-ops-self]].

2. **Параллельный воркер** — `drainQueue(db, concurrency)` (worker.ts), N воркеров разом (claimTask уже FOR UPDATE SKIP LOCKED). Конкурентность в config/queue.ts (QUEUE_CONCURRENCY, по умолч. 5). Турнир ~50с → ~10с. Тюнить вместе с пулом Prisma (connection_limit).
3. **Живая страница** турнира — общая картина НАВЕРХУ с плейсхолдером, раздачи всплывают по очереди; live-refresh.tsx опрашивает статус (расширенный /api/tournament/[id]/status: summaryReady/handsReady/handsTotal), потолок 80 опросов. Поллинги ожидания 3000→1200мс (диалог/чат), 3000→1500мс (парсинг). Блоки раздач переподписаны: «Критические раздачи» (тренер задаёт вопрос) vs «Сильные и средние раздачи» (разбор готов, спроси сам).
Проверки: tsc чисто, 331 тест зелёный (+ __tests__/queue/drain.test.ts), build ОК. Схему БД не трогал — миграция не нужна.

**🔧 ИНЦИДЕНТ+ФИКС 2026-07-01 (пачка 10+ турниров тормозила ~2 мин):** причина — `QUEUE_CONCURRENCY=10` при пуле Prisma по умолчанию **5** (`connection_limit` не был задан; прод-БД на самом деле ЛОКАЛЬНАЯ `localhost:5432/trener_prod`, max_connections=100, НЕ Managed). 10 лейнов дрались за 5 соединений → `Unable to start a transaction in the given time` (видно в pm2 error-логе) → падение задач → ретраи с backoff → минуты. config/queue.ts прямо предупреждает про этот случай. Парсинг ни при чём (замер: 5мс/файл 190КБ/110 рук). Фикс (env, без деплоя, 2 шага): сначала `QUEUE_CONCURRENCY=10→5` + `connection_limit=15` к DATABASE_URL; затем 2026-07-02 по просьбе Артёма вернул `QUEUE_CONCURRENCY=5→10` (пул 15 теперь держит: 10 воркеру + запас крону/web, контеншена нет, волна разбора 10 рук снова одна). Бэкапы `.env.production.bak.*`, `pm2 restart --update-env`, /health 200. Прод-БД ЛОКАЛЬНАЯ на VM (localhost:5432/trener_prod, max_connections=100).

**🔧 БАГ+ФИКС «нет таймаута на LLM» (в коде на ветке claude/memberi-bank-md-overview-e2ngg7, ⏳НЕ задеплоено).** Симптомы 2026-07-08 (жалоба Артёма): разбор шёл ~15 мин, «зависло на 18-й раздаче», не пришёл утренний дайджест. Причина: боевой вызов LLM `rawCall` в `infrastructure/adapters/llm/openrouter.ts` шёл `fetch` БЕЗ таймаута (в отличие от `ping()`, где `AbortSignal.timeout` есть). Когда КЗ-релей принимает соединение, но висит (перегрузка/медленный upstream), fetch держится дефолтом undici ~5 мин → лейн воркера занят задачей в PROCESSING всё это время, весь турнир «замерзает», а ретраи очереди (backoff 30с×попытку, до 3) растягивают одну раздачу до ~15 мин. Reaper (`STUCK_PROCESSING_TIMEOUT_MS`=10 мин) не спасает: он гоняется в начале прогона (kick.ts loop), а не во время зависшего drainQueue. И релей — общая точка: дайджест шлёт `safeNotifyAdmin` через тот же релей, поэтому при его деградации отчёт молча не уходит (гипотеза; логов прода из облака не видно). **Фикс (код), 2 захода:**
1. Таймаут: `getLlmCallTimeoutMs()` в `config/llm.ts` (env `LLM_CALL_TIMEOUT_MS`, дефолт 90с, правило 3).
2. Цель Артёма «человек не должен заметить зависание» → мало таймаута, нужен ПОВТОР. Вынес общий помощник `infrastructure/adapters/http/resilient-fetch.ts` (`resilientFetch`): таймаут + быстрый повтор по свежему соединению при ВРЕМЕННОЙ икоте релея (обрыв соединения / 502/503/504/429 от перегруженного nginx — гасится за 300–600мс, человек не видит). Полный таймаут (`AbortSignal 'TimeoutError'`) НЕ повторяется — релей залёг, второй заход снова зависнет; ошибка уходит наверх (в очереди — штатный retry/карантин, у голоса — красная кнопка), лейн воркера не держим ×N. Повторы настраиваются: `LLM_CALL_RETRIES` (дефолт 2), `STT_RETRIES` (дефолт 2). Подключено и к боевому LLM-вызову (`adapters/llm/openrouter.ts` rawCall), и к голосу (`adapters/stt/openrouter.ts` transcribe — у него таймаут уже был, повтора не было). Тесты: `__tests__/adapters/http/resilient-fetch.test.ts` (6 кейсов) + `__tests__/adapters/llm/openrouter.test.ts` (4 кейса, вкл. «502→повтор успешен»); 35 тестов adapters зелёные, tsc чисто. NB: у боевого anthropic-вызова (запасной провайдер) таймаут — SDK-дефолт 10 мин; при нужде обернуть так же. Деплой — по команде Артёма («выкатывай»).
