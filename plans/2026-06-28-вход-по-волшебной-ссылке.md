# Вход и регистрация по «волшебной ссылке» (passwordless / magic link)

**Дата:** 2026-06-28
**Решение Артёма:** полностью без пароля — одна почта, ссылка в письме, и для входа, и для регистрации. Пароль остаётся запасным способом, его не трогаем.

## Боль

Регистрация с паролем + подтверждением — трение на входе. Хочется: ввёл почту → кликнул ссылку в письме → внутри. Без пароля.

## Что уже есть (фундамент)

Поток сброса пароля — почти точная копия нужного: одноразовый токен, в БД только SHA-256-хэш, письмо через Unisender, проверка срока и «использован ли». Сессия — HMAC-SHA256 httpOnly cookie на 30 дней. `passwordHash` в `Player` уже `String?` (аккаунт без пароля схема выдержит).

Опорные файлы:
- `features/auth/password-reset.ts` — генерация/хэш токена, письма (образец).
- `features/auth/actions.ts` — `requestPasswordResetAction`, `resetPasswordAction` (образец потока).
- `features/auth/session.ts` — `createSession`, `requireSession`, HMAC-подпись (переиспользуем для «метки намерения»).
- `config/auth.ts` — сроки и лимиты (TTL/rate-limit добавим сюда, Правило 3).
- `infrastructure/adapters/email/*` + `safeSendEmail` — отправка письма.
- `prisma/schema.prisma` — модели `Player`, `PasswordResetToken`.

## Поток (целевой)

```
1. /enter (или блок на /login) — одно поле email, кнопка «Прислать ссылку для входа»
2. requestMagicLinkAction(email)
   ├─ rate-limit по IP и email (как у сброса)
   ├─ генерим raw-токен (32 байта → 64 hex), храним SHA-256-хэш
   ├─ MagicLinkToken.create { email (нормализованный), tokenHash, expiresAt: +15м, usedAt: null }
   ├─ гасим прежние неиспользованные токены этого email
   ├─ safeSendEmail(buildMagicLinkEmail(email, /enter/verify?token=raw))
   └─ всегда return { success: true }  // анти-перебор, нейтральный текст
3. Клик по ссылке → /enter/verify?token=...  (server action verifyMagicLinkAction)
   ├─ tokenHash = sha256(token); ищем строку
   ├─ если нет / usedAt / expiresAt < now → экран «ссылка недействительна или устарела»
   ├─ помечаем токен usedAt = now (одноразовость)
   └─ РАЗВИЛКА по email:
      ├─ Player существует (closedAt = null) → createSession → redirect в кабинет
      └─ Player нет → ставим короткую подписанную cookie pending_registration
                       { email, exp +15м } (HMAC как session) → redirect /enter/complete
4. /enter/complete — только для регистрации
   ├─ читает email из подписанной cookie (не из URL!)
   ├─ поля: галочка согласия (обязательна) + ник (опционален)
   └─ completeRegistrationAction
      ├─ валидирует cookie (подпись + срок), галочку
      ├─ Player.create { email, termsAcceptedAt: now, nickname, passwordHash: null, sessionsValidFrom: now }
      ├─ чистит pending_registration cookie
      ├─ safeSendEmail(buildWelcomeEmail(email))  // переиспользуем
      └─ createSession → redirect в кабинет
```

### Почему «метка намерения», а не токен в форме регистрации
Токен гасим сразу на клике (одноразовость, нельзя переоткрыть ссылку). Чтобы донести подтверждённый email до экрана согласия, выдаём короткоживущую HMAC-подписанную cookie тем же механизмом, что и сессия. Email берём только из неё, не из URL — пользователь не может подставить чужую почту.

## Безопасность (чек-лист до деплоя)

- [ ] Токен в БД только хэшем (SHA-256), raw живёт лишь в письме.
- [ ] Одноразовость: `usedAt` ставится на клике; повтор — отказ.
- [ ] Срок 15 минут (`config/auth.ts`).
- [ ] Rate-limit по IP и email (переиспользовать `features/auth/rate-limit.ts`).
- [ ] Нейтральный ответ — форма не раскрывает, существует ли почта.
- [ ] Нормализация email (trim + toLowerCase) и при выдаче, и при поиске.
- [ ] Закрытые аккаунты: при закрытии email обнуляется → коллизии нет, повторная регистрация создаёт новый аккаунт.
- [ ] Согласие на обработку данных (`termsAcceptedAt`) фиксируется на шаге complete — без галочки аккаунт не создаётся (Правило безопасности / 07-безопасность).
- [ ] pending_registration cookie: httpOnly, secure(prod), sameSite=lax, срок 15м, подпись HMAC.
- [ ] Самопроверка hardening + security-review куска после приёмки (по правилу проекта).
