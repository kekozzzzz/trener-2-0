## Фаза A — Порядок хода в точке решения [x]  ← приоритет, класс «поломка №2»

**Симптом.** На ривере (борд A K Q 3 2, топ-пара тузов, банк 59 BB) тренер написал игроку: «оба соперника чекают перед тобой». По факту (коуч): Hero на CO, баттон ЗА ним; на ривере был ОДИН чек до Hero, и один игрок ещё сидел позади. Коуч растерялся — «как я мог чекнуть». Споты стратегически разные: «все чекнули, ты закрываешь» ≠ «один чекнул, за тобой живой баттон, который может чек-рейзнуть/сыграть позади».

**Корень.** В промпт модели уходит: список мест с позициями, сырой список `[Действия по улицам]`, и `renderOpponentLines` (линия каждого соперника по улицам). НО детерминированного факта «кто ходил ДО Hero и кто сидит ПОЗАДИ на текущей улице» — нет нигде. Модель достраивает порядок «до/после меня» из сырого списка и путается. Это ровно то, ради чего затевались факты-v2, но недоделано: линии соперников есть, Hero-относительный порядок в точке решения — нет.

**Почему приоритет.** `architecture/00-правила-проекта.md`, поломка №2: LLM переврал детерминированный факт → «один скриншот в Discord». Пусть не число, а порядок хода — класс тот же. Живой игрок такое скринит.

**Фикс (Правило 1).** Парсер отдаёт явную строку в точке решения:
> «На ривере до тебя: BB чек. За тобой ещё не действовали: BTN. Банк 59 BB.»

Тогда модель физически не сможет переврать порядок — как перестала путать линии соперников после факты-v2.

- [x] новый факт в парсере (`parser/action-order.ts` `renderActionOrder`): по каждой постфлоп-улице порядок первого действия = посадочный порядок; место Hero делит на «до тебя: BB чек» и «за тобой ещё не действовали: BTN» (или «за тобой никого — ты закрываешь» / «ты ходишь первым»); чистая функция от снимка, сброс на прошлой улице в «позади» не тянется;
- [x] подключён в `renderTableSnapshot` (`config/prompts/hand-analysis.ts`) — снимок общий для ВСЕХ 4 ролей (разбор/вердикт/вопрос-диалога/чат), фикс долетает и до вопроса диалога, где был баг;
- [x] строка в промпт: правило 1 COACH_FRAMEWORK дополнено — «порядок хода дан строкой, не достраивай сам, кто до/после тебя; „за тобой ещё не действовали“ = ты НЕ закрываешь улицу»;
- [x] тест `__tests__/parser/action-order.test.ts` (5 кейсов, все зелёные): баг коуча (один чек до Hero, баттон позади), Hero закрывает, Hero первый, сброс не тянется в «позади», префлоп-олл-ин → пусто. tsc чист, весь сьют 938 зелёный.

## Фаза B — Выкатить PKO (нокаут-формат) [~]  код готов, выкатка за Артёмом

**Симптом.** Коуч: «ПКО-турнир, а машина разобрана как ваниль, никаких нокаутов не вижу, да ещё посчитано в BB — некорректно».

**Статус.** Уже готово в факты-v2 (фаза 5), НЕ задеплоено. `config/tournament-format.ts` детектит нокаут по названию (реальное имя GG «Bounty Hunters Deepstack» ловит), `renderBountyFact` объясняет модели баунти-динамику, флаг проброшен во все 4 роли, `bountyAdjustedCallPct` считает пот-оддсы с поправкой на голову.

- [x] проверено: GG **не кладёт** сумму головы в HH (в теле нет bounty-маркеров, Seat-строки чистые `(N in chips)`). Значит для GG-нокаутов работает КАЧЕСТВЕННЫЙ баунти-факт (детект по названию → renderBountyFact), а точные адьюстнутые пот-оддсы `bountyAdjustedCallPct` недоступны — не блокер, главная претензия «разобрано как ваниль» закрывается качественным фактом. У PS/Winamax сумма есть → там и адьюстнутые оддсы работают;
- [x] претензия «посчитано в BB» уже закрыта: renderBountyFact прямо велит «назови баунти-фактор явно, не суди такой колл по одним пот-оддсам» (BB как единица остаётся — она верная), отдельная правка не нужна;
- [x] детект для GG подтверждён: имя фикстуры «Bounty Hunters Deepstack Turbo» проходит isBountyTournament (юнит-тест зелёный); e2e на живом GG PKO-файле из Test/ — за Артёмом (файлы вне git, у меня нет);
- [ ] **за Артёмом:** одобрить промпт-изменения (renderBountyFact + COACH_FRAMEWORK факты-v2 + строка порядка хода из фазы A) — правило «спроси разрешения №5»; затем выкатить по команде. Код готов, ничего не задеплоено.

## Фаза C — Сетка: один диапазон / «зачем» = текст [x]

**Симптом.** Вопрос про T8o 3-бет: «какие руки рассчитывал ВЫБИТЬ, а какие ЗАКОЛЛИРУЮТ и ты будешь впереди» — просит ДВА диапазона, а сетка даёт отметить один. Коуч: «неинтуитивно, могу выделить только один».

**Причина.** Модель нарушила СВОЁ ЖЕ правило `config/prompts/hand-analysis.ts` (блок «Сократовский вопрос»): «Вопрос с сеткой — ровно ОДИН диапазон одного соперника и одного действия». Плюс «что ты хотел получить ставкой» — это вопрос-замысел, а он по тому же правилу должен быть текстом (answerMode:text), не сеткой. Двойной промах: сеткой сделали то, что должно быть текстом, да ещё впихнули два диапазона.

**Фикс (дёшево, без UI). [x]** В `config/prompts/dialogue-question.ts` (техническое поле answerMode): (1) расширен список «замысел = текст» — «что ты хотел получить ставкой / на что рассчитывал / какой был план» = text, даже если упоминает руки; (2) явный запрет двух диапазонов на одной сетке — «кого выбиваю» и «кто коллирует» = два разных набора, суть в замысле → текст. Без правки UI.

**Развилка — двойная сетка как ФИЧА (решение Артёма).** Идея Артёма: вместо борьбы с непослушной моделью просто дать UI под два диапазона. Резон есть (UI-ограничение жёстче, чем промпт-правило). Но:
- в ОБОИХ реальных примерах коуча вторая сетка не нужна: в велью-споте с топ-парой крючок один — «кто коллирует хуже и ты впереди» (тонкое велью; «кого выбиваю» второстепенно — не для фолдов ставишь); в T8o-споте вопрос вообще текстовый (замысел);
- двойная сетка узаконит рыхлые двухчастные вопросы, вместо того чтобы чинить причину — один точный вопрос;
- если делать — то как отдельную фичу для истинно ПОЛЯРИЗОВАННЫХ бет-спотов (часть диапазона выбиваю эквити-денаем, часть коллит хуже на велью), и с решённым вопросом, как показываем/оцениваем ОБА диапазона.
- **Рекомендация:** сначала дешёвый фикс (один диапазон / текст). Двойную сетку — позже и только если решим, что двухчастные вопросы желательны.

## Фаза D — Анти-нит на SB (K5o, K6o) [x]  (данные чартов не тронуты)

**Симптом.** K5o опен с SB назван утечкой («открывать не стоит, шире, чем нужно»); K6o долимп с SB за лимпером — «лимп-утечка». Коуч: и то, и то нормально (даже GTO), можно и шире. Это РЕЦИДИВ «анти-нит перекоса» из прошлого coach-аудита — вылезает на самых широких спотах (блайнды, SB).

**Корень.**
- SB рейз-ренж по офсьюту узкий: `config/poker/rfi-chart.ts` (RFI_RAW.SB) — `A5o+, K9o+, Q9o+, J9o+` → K5o вне → грейдер «шире нормы». Но фраза «шире, чем нужно» читается как «рука мусор», хотя по нашей же философии слабые SB-руки ЛИМПЯТ.
- K6o долимп с SB за лимпером падает в общее правило `parser/preflop-chart-fact.ts` («долимп слабее изоляции») без SB-скидки — при том что рядом (детектор SB-лимпа при фолде до Hero) SB-лимп объявлен НЕ-утечкой. Несостыковка: открыться лимпом с SB — ок, а долимпить с SB — вдруг утечка.

**Фикс (без трогания данных чартов). [x]** Всё в `parser/preflop-chart-fact.ts`:
- [x] открытие с SB вне рейз-ренжа: вместо «шире нормы» — «вне SB рейз-ренжа, но НЕ утечка: слабые руки с SB лимпят, а не фолдят; оцени как рейз-vs-лимп, жёстким вердиктом не суди»;
- [x] SB-долимп за лимпером: вместо «слабее изоляции» — «дешёвый комплит из SB, НЕ утечка» (зеркалит «SB-лимп при фолде до Hero не утечка»);
- [x] регресс `__tests__/parser/chart-fact-extra-spots.test.ts` (+3 кейса): K5o-опен с SB не клеймится/предлагает лимп, K6o-долимп с SB не утечка, КОНТРОЛЬ — K5o-опен с HJ по-прежнему «шире нормы» (правка бьёт только по SB, ранние позиции не размыты).

**Опция (правка ДАННЫХ чарта, решение Артёма).** Ширить сам SB рейз-ренж под мнение коуча. Требует слова Артёма — ренж собран из его коуч-материалов. Минимальный фикс (подача + долимпы) чинит жалобу и без этого.
