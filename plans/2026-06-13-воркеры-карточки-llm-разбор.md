# Воркеры карточки: сохранение всех раздач + LLM-разбор отобранных + CARD_READY

**Дата:** 2026-06-13
**Статус:** в работе

> Реализует шаги 2–4 из [[../architecture/04-потоки-данных]] раздел 5: `PARSING → PARSED → CARD_READY`.
> Опирается на готовые `selectHandsForCard` ([[2026-06-13-отбор-раздач-для-карточки]]) и схему `hands` с `selected_for_card`/`analysis` ([[../architecture/03-база-данных]]).

---

## Контекст

Сейчас `PARSE_TOURNAMENT` (`infrastructure/queue/steps/parse-tournament.ts`) только обновляет три метрики турнира и переводит статус в `PARSED`. Раздачи в `hands` не сохраняются вообще. `uploadTournament` парсит файл синхронно, но в payload задачи кладёт только три агрегата — полный `ParsedTournament.hands[]` отбрасывается.

Нужно дотянуть до конца: все ~70 раздач в `hands`, ~10 отобранных помечены `selected_for_card`, для них фоново сгенерирован `analysis` через LLM-адаптер, после чего турнир — `CARD_READY`.

---

## Решения

1. **Передача распарсенных раздач воркеру** — `uploadTournament` кладёт в payload `PARSE_TOURNAMENT` весь `ParsedTournament` (метрики + `hands[]` со снимками столов). Парсинг остаётся синхронным и единственным источником чисел (правило 1) — воркер только сохраняет уже посчитанное, не парсит повторно. Файл — текст на десятки КБ, JSONB-payload это держит легко (раздел 5 [[../architecture/03-база-данных]]).

2. **`PARSE_TOURNAMENT`**:
   - идемпотентность — если `hands` для турнира уже существуют (`count > 0`), шаг не создаёт их повторно (защита от повтора после крэша между записью `hands` и постановкой `GENERATE_HAND_ANALYSIS`);
   - обновляет метрики турнира + `styleDiagnosis`, статус → `PARSED`;
   - `selectHandsForCard(hands)` → множество отобранных (по reference, т.к. функция возвращает те же объекты);
   - `createMany` всех раздач с `id` (генерируется в коде, `crypto.randomUUID()` — нужен заранее для постановки задач), `importanceLevel`, `chipResult`, `tableData`, `selectedForCard`;
   - для каждой отобранной раздачи — `enqueue GENERATE_HAND_ANALYSIS {handId}`.
   - всё одной транзакцией.

3. **LLM-адаптер** (`infrastructure/adapters/llm/`):
   - `types.ts` — порт `LlmPort.generateHandAnalysis(request): Promise<HandAnalysisResult>`, типы `HandAnalysisRequest`/`HandAnalysisResult`. Вход — обезличенный снимок стола (уже `Hero`/`Player N`) + посчитанные метрики раздачи и турнира. Выход зависит от `importanceLevel`:
     - `CRITICAL` → `played`, `optimal`, `question` (сократовский вопрос), `draftVerdict` (черновик — НЕ показывается игроку сразу, попадёт в `dialogues.verdict` позже через `GENERATE_VERDICT`, после ответа игрока — правило 2);
     - `STRONG` → `played`, `optimal`, `note` (короткое подтверждение «здесь всё правильно, вот почему»);
     - `MEDIUM` → `played`, `optimal`, `note` (лёгкая заметка «можно было чуть иначе»).
   - `anthropic.ts` — реализация через `@anthropic-ai/sdk` (новая зависимость, подтверждена пользователем). Модель — из `config/llm.ts` (env `ANTHROPIC_MODEL`, дефолт `claude-sonnet-4-6`), не хардкод (правило 3). Просит у Claude чистый JSON, парсит и валидирует по `importanceLevel`; невалидный ответ → ошибка → обычный путь очереди (retry/poison).
   - `fake.ts` — детерминированный фейк для тестов (без сети и расходов), используется когда `ANTHROPIC_API_KEY` пуст или явно в тестах.
   - `index.ts` — `getLlmAdapter()`: возвращает `anthropic` если есть ключ, иначе `fake` (дев-фоллбэк).

4. **Промпт** (`config/prompts/hand-analysis.ts`) — продуктовый контент, черновик сейчас. Обязательные строки правила 1:
   - «Все числа уже рассчитаны парсером и переданы тебе. Не вычисляй метрики самостоятельно.»
   - «Если не уверен в своей рекомендации — не выдавай её как категоричный совет. Сформулируй как уточняющий вопрос игроку вместо готового вердикта.»
   Плюс блок-инструкция, зависящая от `importanceLevel` (вопрос+заготовка / подтверждение / лёгкая заметка), требование JSON-ответа, язык — русский, термины конкретных действий («олл-ин», не «шов» — `feedback_card_language`).

5. **`GENERATE_HAND_ANALYSIS`** (`infrastructure/queue/steps/generate-hand-analysis.ts`), payload `{handId}`:
   - идемпотентность — если `hand.analysis !== null`, задача уже выполнена, выходим без вызова LLM (раздел 4 [[../architecture/04-потоки-данных]] — идемпотентность платных вызовов);
   - читает `hand` + родительский `tournament` (контекст метрик);
   - вызывает `llmAdapter.generateHandAnalysis(...)`;
   - одной транзакцией: сохраняет `hand.analysis`; если `CRITICAL` и есть `question` — upsert `Dialogue {handId, question, state: QUESTION_ASKED}` (готовит почву под сократовский диалог, правило 2 — вердикт не пишется в `dialogues.verdict` на этом шаге);
   - после сохранения — проверяет, остались ли у турнира отобранные раздачи без `analysis`, у которых задача `GENERATE_HAND_ANALYSIS` не `POISONED`; если нет — `tournament.status = CARD_READY` (шаг 4 раздела 5: «все ~10 обработаны — успехом или карантином»).

6. **Регистрация** в `infrastructure/queue/bootstrap.ts`: `registerStep("GENERATE_HAND_ANALYSIS", generateHandAnalysisStep)`.

## Итог

Сделано всё по плану: `PARSE_TOURNAMENT` теперь сохраняет все распарсенные раздачи в `hands`, помечает отобранные `selectHandsForCard` флагом `selected_for_card` и ставит по задаче `GENERATE_HAND_ANALYSIS` на каждую. Этот шаг читает раздачу + метрики турнира, идёт в LLM-адаптер (`fakeLlmAdapter` в деве/тестах, `anthropicLlmAdapter` при наличии `ANTHROPIC_API_KEY`), сохраняет `analysis`, для `CRITICAL` создаёт `Dialogue {question, state: QUESTION_ASKED}` без вердикта (правило 2 не нарушено — `draftVerdict` остаётся внутри `analysis`, в `dialogues.verdict` не попадает). После того как все отобранные раздачи обработаны (успешно или ушли в `POISONED`), турнир переходит в `CARD_READY`.

Добавлены тесты `__tests__/queue/parse-tournament.test.ts` (12 раздач → 10 отобранных, идемпотентность) и `__tests__/queue/generate-hand-analysis.test.ts` (7 кейсов: сохранение анализа, диалог для CRITICAL, CARD_READY только после обработки всех раздач, не блокируется POISONED-раздачами, идемпотентный повтор, ошибка при отсутствии метрик турнира). Обновлён приёмочный тест `upload-tournament.test.ts` — полный цикл от загрузки файла до `CARD_READY` на фикстуре `ggpoker_mtt_rich.txt` (6 раздач, 2 из них CRITICAL → 2 диалога).

`npm test`: 7/7 файлов, 39/39 тестов проходят (5 прогонов подряд для проверки стабильности). `tsc --noEmit` — без ошибок.

Дополнительно найден и исправлен побочный баг: захват задачи воркером (`claimTask`) сравнивал `run_after AT TIME ZONE 'UTC' <= NOW()` без приведения `NOW()` к точности `TIMESTAMP(3)`, из-за округления при записи `run_after` свежепоставленная задача могла на долю миллисекунды не пройти условие (~1.5% по стресс-тесту) — причина редкой нестабильности тестов очереди. Исправлено приведением `NOW()::timestamp(3)`, подтверждено стресс-тестом (0/500 промахов).

Журналы решений обновлены: `architecture/04-потоки-данных.md` (контракт payload `PARSE_TOURNAMENT`, реализация `GENERATE_HAND_ANALYSIS`/`Dialogue`), `architecture/08-структура-кода.md` (структура `infrastructure/adapters/llm/`).
