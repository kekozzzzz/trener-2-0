## Контекст

Фаза 1 разобрала каждую раздачу турнира в `ParsedHand` (`chipResult` + `tableSnapshot`). Теперь нужно то, что [[../architecture/02-сущности]] описывает как обязательные поля:

- **Раздача:** `importanceLevel` — критическая (до 3 за турнир) / сильная / средняя — присваивает парсер
- **Турнир:** `styleDiagnosis` — лузовый / тайтовый / пассивный / агрессивный — присваивает парсер

Эвристика согласована с пользователем на материале `ggpoker_mtt_rich.txt`:

**Сложность решения** — раздача «спорная» (`isContested`), если Hero сделал `CALL`/`RAISE`/`ALL_IN` **после того как кто-то другой уже добровольно вложил фишки** в этой раздаче (`CALL`/`BET`/`RAISE`/`ALL_IN`, не считая постов анте/блайндов). Без эквити/солвера (сознательно отвергнут — [[../architecture/05-стек]] раздел 10) — это структурный признак «Hero реагировал на чужие действия», а не «открывал в пустоту».

**Стилевой диагноз** — один из 4 (LOOSE/TIGHT/PASSIVE/AGGRESSIVE), выбирается по наибольшему отклонению от базовых ориентиров для микролимитного MTT (early-stage solid reg: VPIP/PFR ≈ 19/17–25/23 — pokercoaching.com, blackrain79.com; малый разрыв VPIP-PFR = агрессивный, большой = пассивный).

export type HandImportance = "CRITICAL" | "STRONG" | "MEDIUM";

## Алгоритмы (`parser/ggpoker/classify.ts`, новый файл)

### 1. `isContestedDecision(actions: TableAction[]): boolean`

Идём по `actions[]` по порядку. Помечаем `seenVoluntary = true`, когда встречаем действие **не-Hero** с типом `CALL`/`BET`/`RAISE`/`ALL_IN`. Если встречаем действие **Hero** с типом `CALL`/`RAISE`/`ALL_IN` при `seenVoluntary === true` — возвращаем `true`.

### 2. `assignImportanceLevels(hands: ParsedHandSnapshot[]): HandImportance[]`

- Кандидаты в **CRITICAL**: `isContested && chipResult < 0`, сортировка по `|chipResult|` убыв., первые 3 → `CRITICAL`, остальные → `MEDIUM`.
- Кандидаты в **STRONG**: `isContested && chipResult > 0` → все `STRONG` (ограничение числа «сильных» для карточки — отдельная задача отбора, см. «Не входит»).
- Всё остальное → `MEDIUM`.

### 3. `computePfrPercent` (в `index.ts`, по аналогии с `heroPlayedPreflop`)

Новый regex `/^Hero: raises/m` на префлоп-сегменте раздачи (тот же сегмент, что в `heroPlayedPreflop`). `pfrPercent = раздачи_с_префлоп_рейзом_Hero / handsCount * 100`, округление как у `vpipPercent` (2 знака).

### 4. `computePostflopAggressionFactor(hands): number`

По всем `tableSnapshot.actions` всех раздач, где `street !== "PREFLOP"` и `actor === "Hero"`:
- `aggressive = count(action ∈ {BET, RAISE})`
- `calls = count(action === CALL)`
- `AF = aggressive / Math.max(calls, 0.5)` (избегаем деления на 0; `ALL_IN` исключён из обоих счётчиков — постфлоп всё-ин может быть и рейзом, и коллом, тип это не различает, и эта неоднозначность сознательно не разрешается в этой фазе)

### 5. `diagnoseStyle(vpipPercent, pfrPercent, postflopAggressionFactor): PlayerStyle`

Пороги (константы в `classify.ts`, ориентир — early-stage solid reg микролимитного MTT):

```typescript
const VPIP_LOOSE_THRESHOLD = 25;   // %, выше — лузовый
const VPIP_TIGHT_THRESHOLD = 19;   // %, ниже — тайтовый
const PFR_GAP_PASSIVE_THRESHOLD = 6; // п.п. (VPIP - PFR), больше — пассивный
const POSTFLOP_AF_AGGRESSIVE_THRESHOLD = 3; // AF выше — агрессивный
```

Считаем 4 скора отклонения от порога:
```
looseScore      = vpipPercent - VPIP_LOOSE_THRESHOLD
tightScore      = VPIP_TIGHT_THRESHOLD - vpipPercent
passiveScore    = (vpipPercent - pfrPercent) - PFR_GAP_PASSIVE_THRESHOLD
aggressiveScore = postflopAggressionFactor - POSTFLOP_AF_AGGRESSIVE_THRESHOLD
```
Возвращаем метку с максимальным скором; при равенстве — порядок LOOSE > TIGHT > PASSIVE > AGGRESSIVE. Диагноз присваивается всегда — даже если все скоры отрицательны (берём «наименее нормальную» ось).
