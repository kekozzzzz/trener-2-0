# План: эталонный диапазон 3-бета как запасной факт для вердикта

**Дата:** 2026-07-26
**Автор:** Клод
**Статус:** завершён

## Цель

Когда игрок в диалоге НЕ отметил диапазон соперника на сетке, тренер сейчас либо
молчит про диапазон вообще, либо (баг, найден 26.07) выдаёт эквити против ОДНОЙ
вскрывшейся руки, но говорит о нём языком «диапазон/спектр тебя доминирует» —
как будто игрок обязан был знать точную руку соперника. Нужно: подставлять вместо
пропущенной разметки наш эталонный диапазон 3-бета (с поправкой на тип конкретного
соперника, если он известен), считать по нему честное эквити, и чётко помечать этот
факт как ОЦЕНКУ для внутреннего расчёта — не выдавать игроку как «так и было».

## Контекст

Разбор конкретной раздачи (22.07-26.07, диалог `ff1eeb7f-fd7...`, hand
`179eec8d-363f...`): Hero открылся с HJ, CO сделал 3-бет, Hero пошёл олл-ин на 30bb
и проиграл AA. В вопросе тренер попросил игрока отметить диапазон 3-бета CO на
сетке — игрок вместо этого ответил текстом («тут я, скорее всего, ошибся»), сетку
не тронул. `buildRangeReads` (range-facts.ts) в таком случае просто пропускает
раунд — ни диапазона, ни эквити против диапазона в фактах нет. Но у вердикта был
ДРУГОЙ реальный факт — `preflopAllInEquityLine` (parser/facts.ts) считает точное
эквити Hero против КОНКРЕТНОЙ вскрывшейся руки соперника (AA), это готовый честный
факт для случаев доездов/кулеров. Модель взяла этот факт (12.7%, посчитано верно —
проверено полным перебором и внешним источником cardfight.com) и заговорила вокруг
него языком диапазона («против такого спектра... нет фолд-эквити»), которого
на самом деле не считали. Итог читается так, будто от игрока требовалось знать
точную руку соперника — это и есть жалоба Артёма.

Разбор с Артёмом (26.07): подставлять в таких случаях НАШ эталонный диапазон
3-бета вместо пропущенной разметки. Уже есть всё нужное:
- `config/poker/vs-open-chart.ts` — `THREEBET_VALUE`/`THREEBET_BLUFF` по позиции
  3-бетующего (ключ CO/BTN/... — это ПОЗИЦИЯ СОПЕРНИКА, не Hero).
- `parser/opponent-profile.ts` — тип соперника NIT/FISH/LAG/REG по VPIP/PFR,
  уже считается и передаётся в `opponents` (generate-verdict.ts).
- `parser/range-equity.ts` (`equityVsRange`) — тот же движок эквити, что и для
  реально отмеченного игроком диапазона.

Артём: пассивный соперник (NIT) → диапазон уже нашего эталона → эквити Hero
ниже; агрессивный (FISH/LAG) → диапазон шире → эквити выше. И главное условие:
это «эталон для нас» (расчёт), а не «эталон для человека» — игроку нельзя подавать
как «ты обязан был это знать».

**Область применения (сознательно узкая):** только спот «Hero открылся одним
рейзом → ровно один соперник сделал 3-бет → Hero отвечает» — под него есть готовый
чарт `vs-open-chart.ts`. Постфлоп-диапазоны, диапазоны опена/изоляции/сквиза и т.п.
в эту задачу НЕ входят — для них либо нет статического чарта (постфлоп — сознательно
без чарта, только разметка игрока, решение 2026-07-03), либо это отдельная задача.
Расширять сразу на всё — риск «каши», о которой предупредил Артём.

## Фазы

### Фаза 1. Детектор «Hero открылся → получил 3-бет» (~40 мин)
- [x] `parser/vs-open-3bet-faced.ts` (новый файл, зеркало `vs-open.ts`, но с другой
      стороны стола): вход — `TableSnapshot`; проверка — Hero первым добровольным
      действием на префлопе делает RAISE (открытие), после него РОВНО один
      оппонент отвечает RAISE (3-бет) БЕЗ чужих колов/рейзов между ними, дальше —
      действие Hero (фолд/колл/олл-ин, не грейдим какое именно — это делает
      сама модель по фактам). Возврат: `{ heroPosition, threebetterSeatLabel,
      threebetterPosition }` или `null`, если спот не подходит (лимп/сквиз/несколько
      входов и т.п. — как в `detectHeroVsOpen`, но зеркально).
- [x] Юнит-тесты детектора: чистый 3-бет (наша раздача — эталон теста), сквиз с
      третьим игроком (→ null), кол вместо 3-бета (→ null), 3-бет от BB (не наш
      спот — BB защищается по своему чарту, отдельно проверить границу).

### Фаза 2. Эталонный диапазон соперника с поправкой на тип (~40 мин)
- [x] `config/poker/vs-open-chart.ts`: экспортировать функцию
      `referenceThreeBetRange(position, opponentType?)` — база `THREEBET_VALUE[pos]
      ∪ THREEBET_BLUFF[pos]` (через существующий `buildRange`); тип NIT → берём
      только `THREEBET_VALUE` (без блефа); FISH/LAG → база + один шаг
      `withTolerance` (та же функция, что уже используют все чарты, не изобретаем
      новую ширину); REG/нет данных/`confidence !== "solid"` → база как есть.
      Порог `confidence` обязателен — «tentative» на малой выборке рук не подстраиваем,
      чтобы не гадать по 3 раздачам.
- [x] Юнит-тесты: NIT уже базы, FISH/LAG шире базы, REG/tentative/нет типа = база
      без изменений, снапшот кодов диапазона для стабильности (regression).

### Фаза 3. Синтетический RangeRead в range-facts.ts (~50 мин)
- [x] Тип `RangeRead` (`infrastructure/adapters/llm/types.ts`): добавить поле
      `estimated: boolean` (реально отмеченный игроком — `false`, подставной
      эталон — `true`).
- [x] `buildRangeReads`: когда `{{range}}`-раунд есть, а `extractRangeNotation`
      не дал кодов (текстовый ответ вместо сетки) — ПЕРЕД тем как молча
      пропустить раунд, пробуем детектор Фазы 1 на `tableSnapshot`. Спот подошёл →
      берём тип соперника из `opponents` по `threebetterSeatLabel`, зовём
      `referenceThreeBetRange`, считаем `equityVsRange`/`rangeBuckets` ТЕМ ЖЕ
      кодом, что и для игрока (той же ветки, только вход другой) и кладём
      `RangeRead` с `estimated: true`. Спот не подошёл (не 3-бет-vs-open) —
      как раньше, факта нет, ничего не выдумываем.
- [x] Юнит-тесты: нашей раздачи (текстовый ответ вместо сетки, 3-бет-vs-open) →
      RangeRead с `estimated:true` и ожидаемым числом эквити; постфлоп-раунд с
      нераспознанной нотацией → по-прежнему пропуск (фича не расширяется туда).

### Фаза 4. Промпт: не выдавать оценку за факт (~30 мин)
- [x] `config/prompts/hand-analysis.ts` (`renderRangeReads`): для `estimated:true`
      явно подписывать блок «Эталонный диапазон (не то, что отметил игрок —
      статистическая оценка по нашим чартам{, подстроена под тип соперника})»,
      отдельно от блоков с реальной разметкой игрока.
- [x] `config/prompts/verdict.ts`: новая инструкция в «Как собрать вердикт» —
      если единственный источник по диапазону это ОЦЕНКА (`estimated`) и/или
      эквити против ОДНОЙ вскрывшейся руки (`preflopAllInEquityLine`), а не
      разметка игрока: говорить «по статистике/обычно» и «как выпало в этот раз»,
      НЕ «диапазон тебя доминирует» без уточнения, что это оценка, и НЕ смешивать
      «оценочный диапазон» с «вот что было на самом деле у конкретного соперника»
      в одном безусловном утверждении. Это ЗАПРОС ИЗМЕНЕНИЯ ПРОМПТА В ПРОДЕ —
      показать формулировку Артёму перед деплоем (правило проекта, раздел «Спроси
      разрешения»).

## Риски

- **Ложное срабатывание детектора** (спутать 3-бет-vs-open со сквизом/иным
  споттом) → тест-кейсы на все соседние сценарии в Фазе 1, детектор возвращает
  `null` при малейшей неоднозначности (как и его зеркало `detectHeroVsOpen`).
- **Слишком уверенный тон промпта для ОЦЕНКИ** → отдельная явная инструкция
  Фазы 4 и ручная проверка текста перед деплоем.
- **Соблазн расширить на другие споты сразу** → сознательно не делаем в этом
  плане (см. «Область применения»); если понадобится — новый план.
