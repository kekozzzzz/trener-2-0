# План: сводная характеристика игрока в личном кабинете

**Дата:** 2026-06-25
**Статус:** ожидает разрешения на схему БД и промпт

---

## Цель

В личном кабинете (страница «Аккаунт») показывать связный текст-характеристику
игрока, собранный по **всем** загруженным турнирам: общий стиль, как часто заходит
в банк, какие руки с каких позиций открывает слишком широко. В конце —
пометка про точность: характеристика становится надёжной примерно от 10 турниров.

Пример тона (со слов Артёма): «ты агрессивный и заходишь слишком часто с подобными
руками с таких-то позиций…». Поведенческие риды вроде «не веришь большим ставкам»
— **второй шаг** (новые считалки парсера), в этот план не входят.

## Решения (зафиксированы)

- **Глубина шага 1:** только на уже посчитанных числах (стиль, средний VPIP,
  открывашки шире нормы). Никаких новых поведенческих метрик — минимум риска по
  правилу 2.
- **Где показывать:** страница «Аккаунт» (`app/account/page.tsx`).

## Что уже есть (фундамент)

- `Tournament.styleDiagnosis` — стиль по турниру (LOOSE/TIGHT/PASSIVE/AGGRESSIVE),
  считает `parser/ggpoker/classify.ts:diagnoseStyle`.
- `Tournament.vpipPercent`, `handsCount`, `resultBuyins` — метрики турнира.
- Открывашки шире нормы — детерминированно: `parser/open-raise.ts:detectHeroOpen`
  + `config/poker/rfi-chart.ts:isOpenSignificantlyWide`. Логика агрегации уже
  написана в `generate-tournament-summary.ts:collectOpenLeak` (по одному турниру).
- `PlayerProfile` (1:1 с игроком) — таблица под эту сводку уже в схеме, но **пустая**
  (нигде не заполняется): `avgVpip`, `avgResultBuyins`, `avgHandsCount`,
  `tournamentsCounted`, `recalculatedAt`.

## Что считает код детерминированно (правило 1 — LLM числа не трогает)

Новая функция-агрегатор по всем не удалённым турнирам игрока со статусом
PARSED/CARD_READY и заполненными метриками:
- `tournamentsCounted` — сколько турниров вошло в расчёт;
- `avgVpip`, `avgResultBuyins`, `avgHandsCount` — средние;
- распределение стилей (счётчик по 4 стилям) → доминирующий стиль;
- агрегированные открывашки шире нормы по **всем раздачам всех турниров**
  (переиспользуем логику `collectOpenLeak`, но на всём наборе раздач игрока),
  топ-N руки+позиции с частотой.

LLM получает готовый JSON этих фактов и только формулирует текст. Пометку про
«надёжно от 10 турниров» рисует UI детерминированно по `tournamentsCounted` —
не доверяем счёт модели (правило 1).

## Изменение схемы БД (нужно разрешение №2)

В `PlayerProfile` добавить одно поле под готовый текст:

```prisma
characteristic String? @map("characteristic") // сводный текст-характеристика; NULL пока турниров нет
```

Существующие поля (`avgVpip`, `tournamentsCounted`, `recalculatedAt`, …) наконец
начинают заполняться. Миграция — новый файл, без удаления данных.

## Новый шаг очереди: GENERATE_PLAYER_CHARACTERISTIC

- payload `{ playerId }`.
- Ставится в конце `generate-tournament-summary.ts` (после сохранения обзора
  турнира) — т.е. при готовности карточки очередного турнира.
- Тело: считает агрегаты → если `tournamentsCounted` не изменился с прошлого раза
  и `characteristic` уже есть → пропуск (идемпотентность + контроль расходов).
  Иначе зовёт LLM, upsert в `PlayerProfile` (текст + средние + счётчик +
  `recalculatedAt`).
- Атрибуция расходов: строка `LlmUsage` со `step = "PLAYER_CHARACTERISTIC"`.
- Регистрация: одна строка в `infrastructure/queue/bootstrap.ts`.

## Новый LLM-промпт (нужно разрешение №5)

`config/prompts/player-characteristic.ts` по образцу `tournament-summary.ts`:
обязательная строка «все числа уже посчитаны, не вычисляй»; называть только
переданные руки/позиции открывашек; русский, на «ты», конкретные действия без
метафор; вернуть строго `{"characteristic": "..."}`. Полный текст промпта — на
отдельное согласование перед написанием кода.

Новый метод порта `generatePlayerCharacteristic` в `LlmPort`, реализация в
`anthropic.ts` и `fake.ts` (+ типы запроса/ответа в `llm/types.ts`).

## Порог точности (правило 3 — в конфиг, не в код)

`config/poker` или `config/app.ts`: `PLAYER_CHARACTERISTIC_RELIABLE_FROM = 10`.
UI ниже порога: «Картина предварительная — уточнится примерно от 10 турниров».
На пороге и выше — без оговорки (или «характеристика устойчивая»).

## UI: страница «Аккаунт»

Новая секция вверху (под Email): заголовок «Твой профиль игры», абзац-текст
характеристики, под ним мелким — пометка про точность и число учтённых турниров.
Если турниров 0 / характеристика ещё не собрана — приглашение загрузить турнир.
Дизайн строго по `design/design-system.md` (text-body, border, secondary).

## Итог

Фича собрана и протестирована, НЕ задеплоена. Числа считает агрегатор детерминированно
(стиль, средний VPIP, открывашки шире нормы по всей дистанции), LLM формулирует текст,
пометку «точно от 10 турниров» рисует страница «Аккаунт» по счётчику турниров.
Пересборка ставится фоном при готовности карточки очередного турнира, идемпотентна по
числу турниров. Осталось до деплоя: применить миграцию на проде, перезапустить локальный
dev-сервер (подхватить новый Prisma-клиент), отдельный hardening-проход, показать промпт
Артёму вживую. Работа шла на фоне параллельной фичи (лимпы/glossary/llm-proxy-worker) в
том же репозитории — конфликтов нет, общий `tsc`/тесты/билд зелёные.

## Риски и правила

- Правило 1/2: все числа и сверка открывашек — только код; LLM формулирует.
- Правило 3: порог и тексты — в конфиге.
- Стоимость: +1 платный вызов на турнир; гасим идемпотентностью по счётчику.
- IDOR: профиль читаем только по `playerId` из сессии.
