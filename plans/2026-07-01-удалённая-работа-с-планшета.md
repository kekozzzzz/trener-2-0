**Статус (2026-07-02):** Часть A (кодинг с планшета) — готова к использованию, нужен только пуш перед отъездом. Часть B (деплой с планшета) — **Фаза 1 сделана (разведка), Фазы 2-5 НЕ НАЧАТЫ.** Артём одобрил направление (деплой с планшета через релей-бота), но делать решил позже сам. Прод-серверы НЕ трогали.

## Часть B. Деплой с планшета через телеграм-бота

### Что уже есть (проверено в коде)

Бот **@whygrid_bot** (код в репозитории) уже защищён двумя слоями:

1. **Секрет вебхука** — `app/api/webhooks/telegram/route.ts:10-13`: запрос без секретного токена в заголовке отлетает 401.
2. **Проверка chat_id** — `infrastructure/posting/webhook.ts:31-33`: команду исполняет только Артём. Чужие сообщения бот НЕ исполняет, а пересылает как отзыв (`webhook.ts:86-101`).

То есть команду деплоя мы вставляем в готовый защищённый механизм, а не строим новую дырявую кнопку.

### 🔑 Ключевая находка Фазы 1 (2026-07-02)

**Сегодняшний деплой СТАРТУЕТ с компьютера Артёма** (`git bundle` локально → доставка на прод-ВМ через КЗ-релей → сборка + `pm2 restart`). Значит при выключенном ПК так деплоить нельзя — бандлу неоткуда взяться.

**Почему нельзя «пусть ВМ сама подтянет с GitHub»:** прод-ВМ (81.26.186.177, РФ) не достаёт ни до GitHub, ни до Telegram. Единственная всегда-включённая машина, которая достаёт **и до GitHub, и до Telegram, и до ВМ** — это **казахстанский релей (92.60.75.87)**, он же jump к ВМ.

**Вывод: «кнопку деплоя» переносим с ПК Артёма на релей.** И это ровно та машина, где **уже крутится бот-сторож @kekoz_bot** и уже общается с Telegram. Значит команду деплоя вешаем на релей-сторож, а НЕ на webhook @whygrid_bot внутри приложения на ВМ (с ВМ деплой невозможен — нет GitHub).

**Тонкости, которые скрипт обязан учесть:** билд на ВМ (1.9 ГБ RAM) при работающем `trener` падает по OOM/гонке за `.next` → безопасно `pm2 stop trener` → бэкап `.next` ВНЕ дерева → `rm -rf .next` → `build` → `restart`; миграции только `prisma migrate deploy`; SSH-джамп через `ProxyCommand`.

## Техсправка для реализации (чтобы поднять план без моей памяти)

Точные детали текущего деплоя (источник — память project_deploy_procedure; в git её нет, поэтому дублирую сюда):

- **Серверы:** прод-ВМ `81.26.186.177` (Yandex Cloud, РФ, не достаёт до GitHub/Telegram); КЗ-релей `92.60.75.87` (достаёт до GitHub, Telegram и ВМ; jump-host). Бот-сторож @kekoz_bot и Telegram-прокси `/tg/` уже крутятся на релее. Admin chat_id `440359604`.
- **SSH к ВМ (рабочая форма через ProxyCommand, `-J` давал Host key verification failed):**
  `ssh -i ~/.ssh/id_ed25519 -o StrictHostKeyChecking=accept-new -o "ProxyCommand=ssh -i ~/.ssh/id_ed25519 -o StrictHostKeyChecking=accept-new -W %h:%p root@92.60.75.87" -l trener-vm 81.26.186.177`
- **Инкрементальный бандл сегодня (с ПК):** `git bundle create hf.bundle <prod-commit>..master` → scp через тот же ProxyCommand → на ВМ `git fetch <bundle> master && git merge --ff-only FETCH_HEAD`. **В новой схеме бандл собирает РЕЛЕЙ** (он свежий код берёт с GitHub сам).
- **Безопасная сборка на ВМ (1.9 ГБ RAM, swap поднят до 6 ГБ):** сначала попробовать `npm run build` без остановки; при падении OOM/`.next` — `pm2 stop trener` → `mv .next /tmp/next.bak` (бэкап ВНЕ дерева trener/, иначе попадает под tsc-скан) → `rm -rf .next` → `npm run build` → `pm2 restart trener`. При провале — вернуть бэкап и поднять.
- **Миграции:** только `prisma migrate deploy` (НЕ `migrate dev` — портит ручные partial-индексы).
- **Приложение под pm2:** `pm2 restart trener`, `pm2 logs trener`.
- **Правило:** прод-операции Клод делает сам через релей-jump (feedback_server_ops_self); тесты парсера перед выкаткой обязательны (Запрет 4).
