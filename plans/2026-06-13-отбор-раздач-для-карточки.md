# Адаптивный отбор раздач для карточки

**Дата:** 2026-06-13
**Статус:** готово

> Закрывает открытый пункт «бэклог» из [[2026-06-13-классификация-раздач-стиль]]: «адаптивный отбор ~10 раздач для карточки (соотношение критическая/сильная/средняя по качеству сессии)».

---

## Контекст

Парсер уже размечает **все** раздачи турнира (`ParsedTournament.hands: ParsedHand[]`, ~70 штук) полем `importanceLevel: CRITICAL | STRONG | MEDIUM` (`parser/ggpoker/classify.ts`, `assignImportanceLevels`). CRITICAL уже ограничен до 3 на турнир.

[[../idea/mvp]] требует для карточки ~10 раздач с адаптивным соотношением:
- отличная сессия: ~1 критическая + ~5 сильных + ~4 средних
- обычная сессия: ~3 критических + ~2 сильных + ~5 средних
- провальная сессия: до 3 критических + ~1 сильная + ~6 средних

[[../architecture/02-сущности]] (раздел 3): «Турнир → Раздача: один турнир — много раздач (из ~70 рук турнира отбирается ~10 для разбора)».

**Решено с пользователем (2026-06-13):**
- `ParsedTournament.hands` остаётся **полным** списком всех размеченных раздач — не меняется. Это нужно для будущего режима «Тренировка» ([[../idea/mvp]], «Зафиксированные идеи»): чем больше раздач сохранено, тем точнее в будущем профиль игрока по большим объёмам рук (10К–100К+).
- Отбор ~10 для карточки — **отдельная чистая функция** в `features/card`, работает над полным `hands[]`. Парсер не меняется.
- Никакой отдельной «оценки качества сессии» не нужна: соотношения из `mvp.md` получаются как следствие одной формулы, применённой к реальным данным (CRITICAL/STRONG уже привязаны к результату раздачи через `isContestedDecision` + знак `chipResult`).
- Что из полного `hands[]` сохранять в БД (все ~70 или только отобранные ~10) — отдельный вопрос схемы БД, требует разрешения по правилам проекта (`architecture/00-правила-проекта.md`, «Спроси разрешения»). Не решается в этой задаче.

---

## Контракт (новый)

```typescript
// features/card/select-hands.ts

const CARD_TARGET_TOTAL = 10;
const CARD_MAX_STRONG = 5;

export function selectHandsForCard(hands: ParsedHand[]): ParsedHand[]
```

Вход — полный список размеченных раздач турнира. Выход — подмножество (~10 или меньше, если раздач в турнире меньше), **в хронологическом порядке исходного турнира** (не сгруппированное по уровню важности — порядок важности виден через `importanceLevel` каждой раздачи).

---

## Алгоритм

```
critical   = hands.filter(importanceLevel === "CRITICAL")          // уже ≤ 3, от classify.ts
strongPool = hands.filter(importanceLevel === "STRONG")
               .sort by chipResult desc                              // лучшие выигрыши первыми
mediumPool = hands.filter(importanceLevel === "MEDIUM")
               .sort by |chipResult| desc                             // крупные исходы первыми

remainingAfterCritical = CARD_TARGET_TOTAL - critical.length
strongTake = min(strongPool.length, CARD_MAX_STRONG, remainingAfterCritical)
remainingAfterStrong   = remainingAfterCritical - strongTake
mediumTake = min(mediumPool.length, remainingAfterStrong)

selected = critical ++ strongPool[:strongTake] ++ mediumPool[:mediumTake]
result   = selected, отсортированные по исходному индексу раздачи в hands[]
```

**Почему одна формула покрывает все три сценария mvp.md** (`CARD_MAX_STRONG = 5`):
- отличная (1 CRITICAL, много STRONG): remaining=9 → strong=min(.,5,9)=5, medium=4 → **1+5+4** ✓
- обычная (3 CRITICAL, 2 STRONG): remaining=7 → strong=2, medium=5 → **3+2+5** ✓
- провальная (3 CRITICAL, 1 STRONG): remaining=7 → strong=1, medium=6 → **3+1+6** ✓

**Честность по сильным раздачам** (mvp.md: «если сильных раздач нет совсем — продукт говорит об этом честно»): если `strongPool.length === 0`, `strongTake = 0` — слоты просто уходят в `medium`, никакая раздача не подменяется под «сильную».

**Если раздач в турнире меньше 10** (как в тестовой фикстуре, 6 раздач): берём всё, что есть — `selected.length < 10`, это нормально, «~10» приблизительно.

## Приёмка

- `npm test` (vitest) — новые тесты на синтетических данных зелёные, старые не ломаются
- `tsc --noEmit` — 0 ошибок

  - раздач < 10 → возвращаются все
  - STRONG = 0 → 0 сильных в выдаче, слоты уходят в средние
  - STRONG > CARD_MAX_STRONG → отбираются топ-5 по `chipResult`
  - итоговый порядок — хронологический (по индексу в исходном `hands[]`)
