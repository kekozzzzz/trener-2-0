# База данных

Здесь — то, как хранятся семь сущностей из [[02-сущности]]: по-человечески (что лежит в каждой таблице и зачем), затем горячие места поиска, неприкосновенные правила, файлы и порядок изменений. В конце — готовая SQL-схема.

Стек ([[05-стек]]) ещё не выбран, поэтому схема — переносимый SQL. Когда стек определится, по этому описанию генерируется `schema.prisma` (или модели Python / SQL-миграции Go) — менять решено здесь не придётся, только формат записи.

## 1. Таблицы по-человечески

### `players` — Игрок

Кто пользуется продуктом. Хранит ровно то, чем человек входит в систему:

- **id** — собственный номер записи
- **email** — логин, по нему узнаём человека и шлём письма; должен быть уникален (два игрока с одной почтой — ошибка данных)
- **пароль (хеш)** — никогда не пароль в открытом виде, только результат хеширования
- **дата регистрации / дата изменения**
- **момент закрытия аккаунта** — когда человек удалил аккаунт; после этого момента email и пароль физически стираются (см. раздел про удаление ниже)

### `player_profiles` — Профиль игрока

Накопленная картина «как игрок обычно играет» — ровно одна штука на игрока, существует с первого дня:

- **id**
- **чей профиль** — ссылка на игрока, у каждого игрока профиль ровно один
- **средний VPIP, средний итог в бай-инах, среднее число рук** — то же самое, что считается в каждом турнире, только усреднённое по истории
- **по скольким турнирам посчитано** — от этого числа зависит, показываем личное среднее или общий ориентир для микролимитов
- **когда пересчитан в последний раз**
- даты создания/изменения

**Как пересчитывать (закрытый открытый вопрос из [[02-сущности]]):** в MVP игрок загружает не больше ~20 турниров в месяц, то есть за год набирается едва ли больше пары сотен турниров на человека — это крошечный объём для базы. При таком масштабе нет смысла вести скользящее среднее с поправками: после каждого нового турнира профиль просто пересчитывается заново — простым усреднением по всем турнирам игрока. Это всегда даёт точный результат без риска накопить ошибку округления, и код проще проверить. К скользящему среднему имеет смысл вернуться, только если объём вырастет на порядки (см. «первое расширение» в [[../idea/mvp]]).

### `tournaments` — Турнир

*(в черновиках продукта эта вещь раньше называлась «сессией» — переименована в «Турнир», см. журнал решений [[02-сущности]]: «сессия» в языке игрока означает вечер из нескольких турниров подряд, и это имя сознательно оставлено свободным под будущую сущность именно такого смысла)*

Один загруженный и сыгранный турнир. Это главный «кирпич»-агрегат: на нём висит готовность карточки, лимит по тарифу и право на удаление всего, что к нему относится.

- **id**
- **кто загрузил** — ссылка на игрока
- **когда сыгран турнир** и **когда загружен** (дата загрузки — это и есть момент создания записи, отдельное поле не нужно)
- **VPIP, количество рук, итог в бай-инах** — три метрики карточки, посчитанные парсером
- **стилевой диагноз** — лузовый/тайтовый/пассивный/агрессивный
- **статус обработки** — загружен → разбирается → разобран → карточка готова, и отдельно — не получилось разобрать (битый файл, неподдерживаемый формат). Без статуса ошибки фоновый разборщик не сможет ни найти следующую задачу, ни перестать пытаться разобрать то, что разобрать нельзя
- **момент мягкого удаления** — когда игрок удалил турнир
- даты создания/изменения

### `hh_files` — ссылка на файл истории рук

Сырой файл, который игрок загрузил. Подробно — в разделе про файлы.

- **id**
- **к какому турниру относится** — у каждого турнира ровно один файл
- **где лежит файл** (путь/ключ в хранилище) и **как называется исходно**
- **размер в байтах**
- **момент физической чистки** — когда исходный файл был удалён из хранилища после того, как стал не нужен (раздел 7 про чистку)
- даты создания/изменения

### `hands` — Раздача

Игровая ситуация, отобранная для разбора. Существует только внутри турнира и удаляется вместе с ним — отдельного флага удаления у неё нет (см. раздел про удаление).

- **id**
- **к какому турниру относится**
- **уровень важности** — критическая / сильная / средняя, присваивает парсер по реальным потерям
- **результат раздачи в фишках** — отдельное число (а не часть общего «снимка»), потому что именно по нему парсер отбирает критические раздачи и по нему карточка сортирует руки; это единственное поле раздачи, которое реально участвует в поиске
- **снимок стола** — карты, действия, всё, что увидел и посчитал парсер; показывается как есть, по частям не ищется, поэтому хранится одним структурированным куском
- **готовый разбор** — что игрок сделал и что было бы оптимально; тоже показывается целиком, отдельные поля не нужны
- даты создания/изменения

### `dialogues` — Диалог

Сократовский обмен по одной раздаче — не больше одного на раздачу.

- **id**
- **к какой раздаче относится** — связь «один к одному»
- **вопрос системы**
- **ответ игрока** (изначально пусто)
- **вердикт/разбор** (изначально пусто)
- **состояние обмена** — задан вопрос → получен ответ → показан вердикт. Это явное поле — единственное, что физически не даёт показать вердикт раньше ответа (правило проекта #2 из [[00-правила-проекта]]: переход «вопрос → вердикт», минуя ответ, должен быть невозможен — а не просто не использоваться в коде)
- даты создания/изменения

### `chat_messages` — Сообщение чата

Свободные вопросы игрока по конкретной раздаче и ответы на них.

- **id**
- **к какой раздаче относится**
- **кто написал** — игрок или система
- **текст**
- **время** — момент создания записи и есть момент отправки, отдельное поле не нужно
- даты создания/изменения

### `subscriptions` — Подписка

Платный доступ — ровно одна текущая подписка на игрока.

- **id**
- **чья подписка**
- **статус** — активна / отменена / просрочена
- **код тарифа** — ссылка на тариф (например, `basic_monthly`); сама цена здесь не хранится и не зашивается в код — она живёт в конфиге/таблице настроек (правило проекта #3), потому что цены могут меняться, а старые подписки не должны от этого пострадать
- **дата начала текущего периода** и **дата следующего платежа**
- **внешний идентификатор в платёжной системе** — по нему ищем подписку, когда приходит сигнал от Stripe
- **момент мягкого удаления**
- даты создания/изменения

### `payments` — журнал платежей

В словаре сущностей такой вещи нет, но без неё нарушается прямое требование «деньги не должны списываться дважды» (запрет 5 + правило проекта про одну проводку на один внешний id). Подписка хранит *текущее* состояние, а это — неизменяемая лента всех денежных событий, на которую опирается бухгалтерия и проверка повторных уведомлений от платёжной системы.

- **id**
- **к какой подписке относится**
- **внешний идентификатор платежа** — тот, что прислала платёжная система; уникален. Если уведомление о том же платеже придёт второй раз (платёжные системы это делают регулярно), повторная запись просто не создастся — деньги не спишутся дважды
- **сумма в минимальных единицах** (центы), **валюта**
- **статус** — успешно / неуспешно / возврат
- **когда платёж произошёл по данным платёжной системы**
- даты создания/изменения

## 2. Частые запросы и индексы

Семь вещей, которые продукт будет делать постоянно — и под каждую точный индекс.

1. **Фоновый разборщик ищет следующий турнир для парсинга** — `статус = «загружен» в порядке загрузки`
   → индекс по `(статус, дата создания)` в таблице `tournaments`, только по неудалённым записям

2. **Игрок открывает список своих турниров / последнюю карточку** — `мои турниры, по дате игры, свежие сверху`
   → индекс по `(кто загрузил, дата игры)` в `tournaments`, только по неудалённым

3. **Перед загрузкой нового файла — проверка лимита тарифа** (не больше ~20 турниров в месяц) — `сколько турниров я загрузил с начала месяца`
   → индекс по `(кто загрузил, дата загрузки)` в `tournaments`, только по неудалённым

4. **Открытие карточки турнира — подгрузка ~10 раздач по уровню важности** — `раздачи этого турнира, сначала критические`
   → индекс по `(турнир, уровень важности)` в `hands`

5. **Ежедневная фоновая проверка подписок на продление/просрочку** — `активные подписки, у которых подошла дата следующего платежа`
   → индекс по `(статус, дата следующего платежа)` в `subscriptions`

6. **Открытие чата по раздаче — подгрузка истории сообщений** — `сообщения этой раздачи по времени`
   → индекс по `(раздача, время создания)` в `chat_messages`

7. **Плановая чистка устаревших HH-файлов** (раздел 7) — `файлы, которые ещё не вычищены, у турниров, чья карточка готова уже давно`
   → индекс по `(момент чистки)` в `hh_files`, только по ещё не вычищенным записям; для отбора «карточка готова уже давно» используется тот же индекс по `(статус, …)` в `tournaments`, что и в пункте 1

## 3. Правила, которые в базе никогда не должны нарушаться

- **Нет ссылок в никуда.** Каждая ссылка (раздача → турнир, турнир → игрок, диалог → раздача и так далее) обязана указывать на существующую запись — это закреплено внешними ключами, база физически не даст создать висячую ссылку.
- **У каждой записи свой уникальный номер.**
- **У каждой таблицы есть дата создания и дата изменения.**
- **Email уникален, пароль хранится только как хеш** — иначе утечка базы означает утечку паролей напрямую (риск из [[00-правила-проекта]]).
- **Удалённое не возвращается в обычных запросах.** Везде, где предусмотрено мягкое удаление, обычные запросы продукта добавляют условие «запись не помечена удалённой» — это часть общего слоя доступа к данным, а не привычка каждого отдельного запроса.
- **Деньги — только целое число в минимальных единицах** (центы), никогда не дробное — иначе округление рано или поздно разойдётся с тем, что списала платёжная система.
- **Один внешний идентификатор платежа = ровно одна проводка** — обеспечивается уникальностью этого идентификатора в журнале платежей; повторное уведомление от платёжной системы не создаст вторую запись и не спишет деньги повторно.

### Режим удаления — осознанно по каждой таблице (не «мягко везде»)

| Таблица | Режим | Почему |
|---|---|---|
| `players` | **Личные поля стираются физически** (email и хеш пароля перезаписываются на момент закрытия аккаунта, восстановить нельзя) | Это персональные данные человека. При этом саму строку не удаляем — она остаётся техническим якорем для записей, которые правило проекта прямо требует хранить (история турниров, подписки — запрет 5). Без этого якоря пришлось бы либо нарушить «нет ссылок в никуда», либо стереть оплаченную историю — оба варианта хуже |
| `hh_files` | **Строка и сам файл удаляются физически** | Это самые чувствительные личные данные продукта — никакнеймы, по которым человека узнают в маленьком покерном сообществе (риск #5 из [[00-правила-проекта]]). Чем раньше физически исчезает файл — тем меньше площадь утечки |
| `tournaments`, `subscriptions` | **Мягкое удаление** (помечаются, скрываются из обычных запросов, физически остаются) | Это прямое требование запрета 5: «нельзя удалять подписку или историю турниров без двойного подтверждения». Это ещё и бизнес-факты с историей — пригодятся для подсчёта профиля, для разбора спорных ситуаций с оплатой, для восстановления по ошибке |
| `hands`, `dialogues`, `chat_messages` | **Отдельного флага удаления нет** — их видимость целиком определяется тем, удалён ли их турнир | Они существуют только внутри турнира и не удаляются по отдельности — добавлять им свой флаг означало бы дублировать состояние турнира и рисковать рассогласованием («турнир мягко удалён, а его раздачи — ещё нет») |
| `payments` | **Никогда не удаляется, не изменяется** (append-only журнал) | Это финансовый журнал для бухгалтерии и разбора платёжных споров — по закону и по здравому смыслу такие записи не трогают вообще, ни мягко, ни жёстко |
| `player_profiles` | **Удаляется физически вместе с аккаунтом** | Это пересчитываемый агрегат, не самостоятельный факт: в нём нет ничего, что нельзя посчитать заново из истории турниров, и нет собственной исторической ценности |

## 4. Файлы

HH-файл, который игрок загружает, — единственный «большой файл» в продукте. Он лежит в отдельном файловом хранилище (на старте — локальный диск, позже, по мере роста, — S3-совместимое хранилище, см. [[06-внешние-сервисы]]; смена места хранения — решение, требующее отдельного согласия по правилу проекта). В базе остаётся только запись `hh_files`: где лежит файл, как называется и сколько весит. Так дешевле — большой бинарный файл не раздувает базу и не замедляет её резервное копирование — и безопаснее: личные данные (никнеймы) физически отделены от остальной базы и могут быть стёрты независимо и быстро (см. таблицу режимов удаления выше).

## 5. Как менять базу позже, не теряя данные

- Каждое изменение схемы — отдельный шаг со своей датой, применяется поверх предыдущих по порядку. Уже применённый на проде шаг никогда не переписывается задним числом — если в нём ошибка, она исправляется новым шагом, а не правкой старого.
- Удаление поля, в котором уже есть данные, — всегда в два захода: сначала код перестаёт писать и читать это поле (но оно остаётся в базе и ничего не ломает), и только отдельным более поздним шагом поле физически убирается из таблицы.
- Не проектируем под объёмы, которых пока нет: при потолке ~20 турниров в месяц и ~70 раздач на турнир (из которых ~10 отбираются для разбора) на одного игрока за год набирается едва ли больше пары тысяч строк суммарно по всем таблицам. Это тривиальный объём для обычных индексов без партиционирования, отдельных хранилищ для «горячих» и «холодных» данных и прочих вещей, которые имеют смысл только при настоящем росте (см. «первое расширение» — полная история на 10–100 тысяч раздач — в [[../idea/mvp]], которое и станет поводом пересмотреть это решение).

## 6. SQL-схема

Стек ещё не выбран ([[05-стек]] — черновик), поэтому ниже переносимый SQL в духе PostgreSQL — самого вероятного кандидата по черновикам других файлов. Когда стек определится, эта схема превращается в `schema.prisma` (Node/TS) или в модели и первую миграцию (Python), без изменения самой структуры — только формы записи.

```sql
-- ───────────────────────── Игрок ─────────────────────────
CREATE TABLE players (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email         TEXT UNIQUE,                 -- NULL после закрытия аккаунта (анонимизация)
  password_hash TEXT,                        -- NULL после закрытия аккаунта
  closed_at     TIMESTAMPTZ,                 -- момент закрытия и анонимизации аккаунта
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────── Профиль игрока (1:1) ─────────────────────
CREATE TABLE player_profiles (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  player_id         UUID NOT NULL UNIQUE REFERENCES players(id) ON DELETE CASCADE,
  avg_vpip          NUMERIC(5,2),
  avg_result_buyins NUMERIC(8,2),
  avg_hands_count   NUMERIC(8,2),
  tournaments_counted INTEGER NOT NULL DEFAULT 0,
  recalculated_at   TIMESTAMPTZ,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────────── Турнир ─────────────────────────
-- (в черновиках назывался «сессией» — переименован в «турнир»: см. журнал решений 02-сущности.
--  имя «session»/«сессия» сознательно оставлено свободным под будущий агрегатор «несколько турниров одного вечера»)
CREATE TYPE tournament_status AS ENUM ('UPLOADED', 'PARSING', 'PARSED', 'CARD_READY', 'FAILED');
CREATE TYPE player_style      AS ENUM ('LOOSE', 'TIGHT', 'PASSIVE', 'AGGRESSIVE');

CREATE TABLE tournaments (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  player_id       UUID NOT NULL REFERENCES players(id) ON DELETE RESTRICT,
  played_at       TIMESTAMPTZ NOT NULL,
  vpip_percent    NUMERIC(5,2),
  hands_count     INTEGER,
  result_buyins   NUMERIC(8,2),
  style_diagnosis player_style,
  status          tournament_status NOT NULL DEFAULT 'UPLOADED',
  deleted_at      TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ─────────────────── Ссылка на HH-файл (1:1 с турниром) ───────────────────
CREATE TABLE hh_files (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tournament_id     UUID NOT NULL UNIQUE REFERENCES tournaments(id) ON DELETE CASCADE,
  storage_key       TEXT NOT NULL,
  original_filename TEXT NOT NULL,
  size_bytes        INTEGER NOT NULL,
  purged_at         TIMESTAMPTZ,              -- момент физической чистки файла
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────────── Раздача ─────────────────────────
CREATE TYPE hand_importance AS ENUM ('CRITICAL', 'STRONG', 'MEDIUM');

CREATE TABLE hands (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tournament_id    UUID NOT NULL REFERENCES tournaments(id) ON DELETE CASCADE,
  importance_level hand_importance NOT NULL,
  chip_result      INTEGER NOT NULL,   -- потеря/выигрыш фишек — посчитал парсер, по этому полю отбор и сортировка
  table_data       JSONB NOT NULL,     -- карты, действия за столом — снимок парсера, целиком для отображения
  analysis         JSONB NOT NULL,     -- готовый разбор: что сделано / что было бы оптимально
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────── Диалог (не более 1 на раздачу) ─────────────────────
CREATE TYPE dialogue_state AS ENUM ('QUESTION_ASKED', 'ANSWER_RECEIVED', 'VERDICT_SHOWN');

CREATE TABLE dialogues (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  hand_id    UUID NOT NULL UNIQUE REFERENCES hands(id) ON DELETE CASCADE,
  question   TEXT NOT NULL,
  answer     TEXT,
  verdict    TEXT,
  state      dialogue_state NOT NULL DEFAULT 'QUESTION_ASKED',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────────── Сообщение чата ─────────────────────────
CREATE TYPE message_author AS ENUM ('PLAYER', 'SYSTEM');

CREATE TABLE chat_messages (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  hand_id    UUID NOT NULL REFERENCES hands(id) ON DELETE CASCADE,
  author     message_author NOT NULL,
  text       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────────── Подписка ─────────────────────────
CREATE TYPE subscription_status AS ENUM ('ACTIVE', 'CANCELED', 'EXPIRED');

CREATE TABLE subscriptions (
  id                       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  player_id                UUID NOT NULL UNIQUE REFERENCES players(id) ON DELETE RESTRICT,
  status                   subscription_status NOT NULL,
  plan_code                TEXT NOT NULL,        -- ссылка на тариф из конфига; цена здесь не хранится (правило проекта #3)
  current_period_start     TIMESTAMPTZ NOT NULL,
  next_payment_at          TIMESTAMPTZ,
  external_subscription_id TEXT NOT NULL UNIQUE,
  deleted_at               TIMESTAMPTZ,
  created_at               TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at               TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────── Журнал платежей (append-only) ─────────────────
CREATE TYPE payment_status AS ENUM ('SUCCEEDED', 'FAILED', 'REFUNDED');

CREATE TABLE payments (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  subscription_id     UUID NOT NULL REFERENCES subscriptions(id) ON DELETE RESTRICT,
  external_payment_id TEXT NOT NULL UNIQUE,   -- один внешний id = одна проводка
  amount_cents        INTEGER NOT NULL,       -- целое число в минимальных единицах валюты
  currency            TEXT NOT NULL,
  status              payment_status NOT NULL,
  occurred_at         TIMESTAMPTZ NOT NULL,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ───────────────────────── Индексы под горячие запросы ─────────────────────────
CREATE INDEX idx_tournaments_pending_parse        ON tournaments (status, created_at)   WHERE deleted_at IS NULL;
CREATE INDEX idx_tournaments_player_timeline      ON tournaments (player_id, played_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_tournaments_player_monthly_count ON tournaments (player_id, created_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_hands_tournament_card            ON hands (tournament_id, importance_level);
CREATE INDEX idx_subscriptions_renewal_check   ON subscriptions (status, next_payment_at);
CREATE INDEX idx_chat_messages_thread          ON chat_messages (hand_id, created_at);
CREATE INDEX idx_hh_files_purge_candidates     ON hh_files (purged_at) WHERE purged_at IS NULL;
```

## Журнал решений

**Решение:** выбрал семь таблиц строго по сущностям из [[02-сущности]] плюс отдельный append-only журнал платежей (`payments`, не входил в словарь сущностей, но напрямую вытекает из требования «один внешний id платежа — одна проводка»), с явным состоянием диалога как полем (а не выводом из наличия ответа), раздельными режимами удаления по таблицам (анонимизация для личных данных игрока, физическое удаление для HH-файлов, мягкое — только там, где это прямо требуют правила проекта про подписки и историю турниров) и переносимой SQL-схемой вместо Prisma — потому что это даёт ровно ту структуру, которую продают правила продукта (точные числа от парсера отдельно от свободного диалога, гарантия «вопрос раньше вердикта» закреплена данными, а не кодом, деньги защищены от двойного списания на уровне ограничения базы), без единой таблицы или поля, добавленных «на всякий случай», и не привязывает решение к стеку, который ещё не выбран.
