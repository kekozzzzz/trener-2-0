# Сущности

Общий словарь продукта. Дальше все шаги (база данных, потоки данных, структура кода) берут названия отсюда.

Контекст: сократовский тренер для микролимитного турнирного игрока GGPoker. Игрок загружает файл истории рук одного турнира → видит карточку с метриками и ~10 раздачами → по важным раздачам с ним ведут диалог «почему ты так сделал?» → он видит разбор и сильные/слабые решения. Подробности — [[01-что-строим]], [[../idea/mvp]].

---

## 1. Список вещей и их определения

| Сущность | Определение в одну строку |
|---|---|
| **Игрок** | человек, который зарегистрировался и загружает свои турниры на разбор |
| **Профиль игрока** | накопленная картина «как игрок обычно играет», посчитанная по всем его турнирам — то, с чем сравнивается каждый новый турнир |
| **Турнир** | один сыгранный МТТ-турнир, разбор которого построен по одному загруженному файлу истории рук |
| **Раздача** | одна игровая ситуация внутри турнира, отобранная для разбора |
| **Диалог** | многораундовый сократовский обмен по конкретной раздаче: серия наводящих вопросов (~5 раундов) → ответы игрока → итог, ведущий игрока к тому, чтобы он сам увидел свою ошибку |
| **Сообщение чата** | свободный вопрос игрока по конкретной раздаче и ответ на него |
| **Подписка** | платный доступ игрока к продукту |

**Уточнение по терминологии (важно не перепутать со словом из лексикона игрока):** здесь и далее «Турнир» — это один сыгранный МТТ-турнир = один загруженный файл истории рук, ровно то, что в MVP загружается и разбирается за раз ([[../idea/mvp]], [[01-что-строим]]). У игроков слово «сессия» означает другое — вечер игры, за который подряд отыгрывается несколько турниров (например, 12 за вечер); такой сущности в продукте пока нет (массовый импорт нескольких турниров разом сознательно не входит в MVP). Имя «Сессия» оставлено свободным намеренно: когда в продукте появится настоящий агрегатор «несколько турниров одного вечера, отыгранные подряд» — он и получит это имя, не сталкиваясь с тем, что сейчас названо «Турнир». См. также журнал решений в конце файла.

## 2. Что мы помним про каждую вещь

### Игрок
- email и пароль (как входит)
- дата регистрации

### Профиль игрока
- какому игроку принадлежит
- накопленные средние по тем же метрикам, что и в турнире: VPIP, итог, количество рук
- по скольким турнирам посчитан (это влияет на то, показываем мы личное среднее или общий ориентир для микролимитов)
- когда пересчитан в последний раз

### Турнир
- кто загрузил (игрок)
- когда сыгран и когда загружен
- исходный файл истории рук
- три метрики: VPIP, количество рук, итог в бай-инах
- стилевой диагноз этого турнира (лузовый / тайтовый / пассивный / агрессивный)
- статус обработки: загружен → разобран парсером → карточка готова

### Раздача
- к какому турниру относится
- карты, действия за столом, потери/выигрыш фишек — то, что посчитал парсер
- уровень важности: критическая (до 3 за турнир, по сочетанию потерь фишек и сложности решения) / сильная / средняя — присваивает парсер
- готовый разбор: что игрок сделал в реальности и что было бы оптимально

### Диалог
- к какой раздаче относится
- последовательность раундов: вопрос системы → ответ игрока (повторяется, на практике ~5 раундов наводящих вопросов)
- итог/разбор, который показывается после последнего ответа
- состояние обмена: текущий раунд (вопрос задан / ответ получен) → показан итог *(нужно явно хранить — это и есть гарантия «итог не раньше ответа», ядро продукта)*

### Сообщение чата
- к какой раздаче относится
- кто написал: игрок или система
- текст
- время

### Подписка
- какому игроку принадлежит
- статус: активна / отменена / просрочена
- тариф (в MVP один: $12/мес)
- дата начала и дата следующего платежа
- внешний идентификатор в платёжной системе

## 3. Связи и их количество

- **Игрок → Турнир**: один игрок — много турниров (загружает турнир за турниром, лимит ~20 в месяц по тарифу)
- **Игрок → Профиль игрока**: один игрок — один профиль (всегда ровно один; заводится вместе с игроком и обновляется после каждого нового турнира — без него нечего ставить рядом с «вчера» в карточке)
- **Игрок → Подписка**: один игрок — одна текущая подписка
- **Турнир → Раздача**: один турнир — много раздач (из ~70 рук турнира отбирается ~10 для разбора)
- **Раздача → Диалог**: одна раздача — не более одного диалога (есть у критических, до 3 за турнир, всегда — это многораундовый диалог; у средних — по запросу игрока; у сильных — короткое подтверждение без полного диалога)
- **Раздача → Сообщение чата**: одна раздача — много сообщений (можно спросить что угодно по конкретной руке)

Аггрегат-владелец здесь — **Турнир**: на нём висит то, что определяет жизненный цикл всей карточки — статус «карточка готова», лимит по тарифу (сколько турниров можно загрузить в месяц), срок хранения и право на удаление. Раздача, Диалог и Сообщение чата — его дочерние части: они не существуют без турнира и удаляются вместе с ним.

## 4. Варианты разложения и гипотеза про «один кирпич»

### Вариант А — семь разных вещей (вариант выше)
Каждая вещь — отдельная сущность со своим набором полей и своим местом в жизненном цикле.

**Плюс:** каждая вещь хранит ровно то, что ей нужно, и ничего лишнего; правила вроде «вердикт показывается только после ответа» легко закрепить явным полем состояния именно в Диалоге.
**Минус:** семь таблиц, семь мест, где нужно продумать поиск/историю/права отдельно.

### Вариант Б — слить «Диалог» и «Сообщение чата» в одну вещь «Обсуждение раздачи»
И то и другое — обмен репликами, привязанный к конкретной раздаче. Можно хранить как один поток сообщений с пометкой типа: «шаг сократовского диалога» или «свободный вопрос».

**Что выигрываю:**
- единый поиск и история по всем обсуждениям одной раздачи
- одна таблица, один экран рендеринга, один экспорт/аудит вместо двух

**Что проигрываю:**
- сократовский диалог — это не просто переписка, а вещь со строгим порядком: нельзя увидеть вердикт, не ответив на вопрос. Если хранить его как обычный список сообщений, эту гарантию придётся восстанавливать логикой поверх данных, а не данными — выше риск, что однажды разработчик случайно покажет вердикт раньше ответа. А именно эта механика — то единственное, что отличает продукт от конкурентов и что в [[../idea/vision]] прямо помечено как «трогать нельзя»

**Вывод:** не сливаю. Цена слияния — размытие главного отличия продукта ради экономии одной таблицы. Не стоит того в MVP.

### Вариант В — попробовать единый «типизированный объект» а-ля Stripe для Раздачи/Диалога/Сообщения
Гипотеза «один-два кирпича» подсказывает попробовать обобщить ещё дальше: всё, что относится к раздаче, — один тип сущности с гибкими полями.

**Что выигрываю:** максимальная гибкость, можно добавлять новые типы обсуждений без миграций.
**Что проигрываю:** Раздача держит на себе как раз те данные, которые обязан точно посчитать парсер (карты, потери фишек, улица) — это ядро доверия к продукту («цифры считает парсер, LLM объясняет», [[../idea/principles]]). Если упаковать их в обобщённый «объект со свойствами», парсеру и проверке станет сложнее гарантировать точность, а ошибка в данных такого типа продукта стоит репутации мгновенно.

**Вывод:** не подхожу. Здесь как раз тот случай, когда один кирпич ломает половину сценариев — домен слишком плотно завязан на точные, типизированные числа.

**Итог по гипотезе:** для этого продукта универсальный кирпич не выигрывает — здесь не текстовый редактор и не таск-трекер, где всё действительно однородно. Здесь два разных по природе вида данных (точные цифры из парсера и свободный диалог), и их разделение — не накладные расходы, а часть того, что продаёт продукт.

## Журнал решений

- **Выделил «Профиль игрока» в отдельную сущность**, а не вычисление на лету — потому что это неотъемлемая часть каждого разбора турнира (строка «вчера / твой средний / оптимально» не работает без него), а не побочное число для статистики. У него собственный момент пересчёта (после каждого нового турнира), своя жизнь с самого первого дня игрока — даже если турниров ещё нет, профиль существует (с пометкой «мало данных, показываем общий ориентир»). Так и закрыл прежний открытый вопрос.
- **Выбрал семь отдельных сущностей** (Игрок, Профиль игрока, Турнир, Раздача, Диалог, Сообщение чата, Подписка) — потому что у каждой свой набор данных и свой жизненный цикл, и слияние любых двух снижает точность ровно там, где она продаёт продукт.
- **Турнир — главный кирпич-агрегат**, а Раздача / Диалог / Сообщение чата — его дочерние части: на турнире висит статус готовности карточки, лимит по тарифу и право на удаление.
- **Отверг** слияние Диалога и Сообщения чата в один поток сообщений — это убрало бы явную гарантию «вердикт только после ответа», которая и есть ядро продукта.
- **Отверг** обобщённый типизированный объект (Stripe-стиль) для Раздачи — домен требует точных типизированных чисел от детерминированного парсера, обобщение мешает гарантировать точность.
- **Пока не знаю**, как именно пересчитывать профиль игрока при росте числа турниров — пересчитывать заново по всей истории или вести скользящее среднее. Решится при проектировании базы данных, когда будет понятен объём данных на игрока.
- **2026-06-07 — переименовал «Сессию» в «Турнир»** по всему проекту: то, что грузится и разбирается за раз — это один турнир (ровно так и описано в [[../idea/mvp]]), а «сессия» в языке игрока означает вечер игры из нескольких турниров подряд — сущность, которой в продукте пока нет (и появится не раньше многотурнирного импорта истории). Старое имя сбивало бы с толку именно тех людей, для кого делается продукт. Имя «Сессия» сознательно оставлено свободным под будущий агрегатор «несколько турниров одного вечера».
- **2026-06-11 — Диалог стал многораундовым** (~5 раундов наводящих вопросов вместо одного цикла вопрос-ответ-вердикт), а уровень «критическая» у Раздачи ограничен до 3 за турнир и определяется не только потерями фишек, но и сложностью решения. Алгоритм определения «сложности решения» — отдельный вопрос для проектирования парсера, пока не решён.
- **2026-06-13 — отбор ~10 раздач для карточки** (`features/card/select-hands.ts`, `selectHandsForCard`) — отдельная функция над полным `hands[]` (все размеченные раздачи турнира), парсер не меняется. Берёт все CRITICAL (≤3, уже ограничено `classify.ts`), до 5 лучших STRONG по `chipResult`, остальное — MEDIUM с наибольшим `|chipResult|`, итог ~10. Одна формула воспроизводит все три соотношения из [[../idea/mvp]] (1+5+4 / 3+2+5 / 3+1+6) без отдельной «оценки качества сессии» — соотношение целиком следствие реальных данных. Если STRONG=0 — слоты честно уходят в MEDIUM, ничего не подменяется. Полный `hands[]` сохранён как есть — нужен будущему режиму «Тренировка» (см. [[../idea/mvp]], «Зафиксированные идеи»). Что из полного списка сохранять в БД — отдельный вопрос, см. [[03-база-данных]].
- **2026-06-13 — открытый вопрос: многораундовый Диалог (решение от 2026-06-11) не реализован.** `GENERATE_VERDICT` (см. [[04-потоки-данных]]) реализован как одна пара вопрос-ответ-вердикт на существующей схеме `dialogues` (`QUESTION_ASKED → ANSWER_RECEIVED → VERDICT_SHOWN`, [[03-база-данных]]) — этого достаточно для текущей карточки и не противоречит правилу 2. Расширение до ~5 раундов наводящих вопросов — отдельная задача: потребует новой схемы (например, таблица сообщений диалога вместо одной пары полей) и, по правилам проекта (CLAUDE.md, «Спроси разрешения» №2), согласия пользователя перед изменением схемы БД.
- **2026-06-13 — открытый вопрос выше закрыт: Диалог стал многораундовым.** `dialogues` теперь хранит только текущее состояние (`verdict`, `state`), а сами раунды — в новой дочерней таблице `dialogue_rounds` (1:N, `UNIQUE(dialogue_id, round_number)`, [[03-база-данных]]). Глубина диалога — фиксированное число из конфига `getDialogueRoundsPerHand()` (`config/dialogue.ts`, по умолчанию 5, одинаково для всех тарифов — решение от 2026-06-11 не пересматривалось). Раунд 1 создаётся `GENERATE_HAND_ANALYSIS` как прежде; раунды 2..N-1 — новой задачей `GENERATE_DIALOGUE_QUESTION` (`LlmPort.generateNextQuestion`); итог на раунде N — `GENERATE_VERDICT`, теперь принимающий всю историю раундов (`VerdictRequest.history`). State-машина `QUESTION_ASKED → ANSWER_RECEIVED → VERDICT_SHOWN` не изменилась — она описывает текущий открытый раунд, а не диалог целиком ([[04-потоки-данных]]).
