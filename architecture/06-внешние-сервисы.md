# Внешние сервисы

Контекст продукта — [[01-что-строим]], процессы и события — [[04-потоки-данных]], выбор технологий и обоснование «почему российские поставщики» — [[05-стек]] (раздел 0 — требование 152-ФЗ), неприкосновенные правила — [[00-правила-проекта]].

Здесь — конкретика подключения каждого внешнего сервиса: с чем сравнивали, что выбрали и почему, что делает продукт при сбое поставщика, и дневной денежный потолок именно по этому сервису. **Общий потолок расходов на весь продукт и автоматический стоп живут в `07-безопасность.md`** — здесь фиксируются только локальные потолки по каждому сервису, как часть общей картины.

Правило 4 ([[00-правила-проекта]]) уже требует: каждый сервис стоит за сменным адаптером в `adapters/<категория>/`, ядро вызывает порт («сгенерируй разбор», «прими оплату», «сохрани файл», «отправь письмо») и не знает, какой конкретно вендор за ним стоит.

## 1. Оплата

### Сравнение вариантов

| Вариант | Цена (комиссия) | Простота подключения | Надёжность |
|---|---|---|---|
| **ЮKassa** | ~3% с обычной карты, ниже у крупных оборотов — рыночная норма для РФ | Готовые SDK под Node.js, документированные вебхуки, рекуррентные платежи «из коробки» — то, что нужно для подписки $12/мес | Самый массовый провайдер в Рунете — через него идут платежи тысяч сервисов, отказ маловероятен и быстро виден по новостям рынка |
| CloudPayments | Сопоставимая комиссия, иногда индивидуальные условия | Специализируется на регулярных платежах — может быть удобнее именно для модели «подписка», но меньше готовых примеров под Next.js | Меньше распространённость → меньше готовых решений тех же проблем, на которые наткнётся именно этот продукт |
| Тинькофф (Т-Касса) / Robokassa | Сопоставимая или чуть выше комиссия, у Robokassa — посредник поверх банков-эквайеров (доп. слой) | Т-Касса требует юрлицо в Тинькофф-банке (доп. завязка на банк); Robokassa проще подключить, но это агрегатор поверх агрегатора — на платежах подписки лишний посредник | Обе работают, но не дают того преимущества «массовость = больше готовых решений и примеров», которое даёт ЮKassa |

### Выбор — поэтапная стратегия

Долгосрочная цель продукта — **международная аудитория из всех стран** (покерные игроки не ограничены Россией). Это определяет трёхфазный план по платёжке:

**Фаза 1 — Сейчас (Россия, самозанятость):** ЮKassa  
Российские игроки платят с российских карт в рублях. ЮKassa — единственный разумный вариант для этого. Деньги поступают на российский банковский счёт.

**Фаза 2 — При первых реальных доходах (триггер, не дата):** открыть ИП в Армении → подключить Stripe  
Не ждать физического переезда. Причина: деньги из ЮKassa лежат на российском счёте, вывести их в Армению сложно из-за санкций и ограничений на трансграничные переводы — это реальная операционная проблема. Stripe с армянским ИП решает её для новых пользователей. Оба адаптера работают одновременно: `adapters/payments/yookassa/` и `adapters/payments/stripe/` реализуют один и тот же порт.

**Фаза 3 — Основной режим (после переезда):** Stripe как главный, ЮKassa закрывается или остаётся для оставшихся RU-подписчиков  
Международный продукт принимает карты всего мира через Stripe (2,9% + $0,30 за транзакцию — 5,4% на $12). Российские подписчики либо мигрируют на Stripe самостоятельно при следующем продлении, либо остаются на ЮKassa до отмены подписки.

**Адаптеры:** `adapters/payments/yookassa/` и `adapters/payments/stripe/` — оба реализуют порт «прими оплату по подписке, сообщи об изменении статуса». Бизнес-логика вызывает порт и не знает, кто за ним стоит. Переключение — конфиг, не переписывание кода (правило 4).

**При миграции подписчиков с ЮKassa на Stripe:** у обеих систем хранятся свои токены карт, прямой перенос невозможен. Работающий путь — пользователь вводит карту при следующем продлении на новом провайдере. Инфраструктурно: добавить флаг `payment_provider` в таблицу `subscriptions`, при продлении роутить на нужный адаптер по этому флагу.

**При недоступности ЮKassa:**
- Создание новой подписки или продление — пользователь видит понятное сообщение «оплата временно недоступна, попробуйте через несколько минут», повтор — рукой пользователя (как и описано в [[04-потоки-данных]] для лёгкой работы №6);
- Уже активные подписки не страдают — статус хранится локально, доступ не отзывается из-за временной недоступности платёжки;
- Вебхук, который не дошёл — не теряется: ЮKassa повторяет доставку; суточная сверка (`RECONCILE_SUBSCRIPTIONS`, событие №11 в [[04-потоки-данных]]) закрывает оставшийся зазор. Для Stripe — та же схема.

**Дневной денежный потолок:** для платёжного провайдера классический «потолок расходов» не применим — комиссия списывается процентом от входящих платежей, то есть пропорциональна выручке, а не является исходящим расходом, который может выйти из-под контроля. Риск здесь не «перерасход», а «простой приёма платежей при сбое» — он закрыт описанным выше поведением и суточной сверкой.

## 2. Почта и уведомления

Здесь две разные задачи с разными адресатами — письма игроку и сигналы администратору (то есть автору продукта). Объединять их в один сервис не нужно: задачи разной критичности и разной срочности.

### 2.1. Транзакционные письма игроку (подтверждение почты, сброс пароля)

| Вариант | Цена | Простота подключения | Надёжность для аудитории |
|---|---|---|---|
| **Unisender Go** (бывший UniOne — отдельный транзакционный продукт Unisender) | Тарификация по числу писем, дешевле полной платформы Unisender — то, что и нужно: продукту не нужны рассылки, только транзакционные письма | Простой REST API специально под транзакционные письма, готовые примеры под Node.js | Давний игрок рынка, отлаженная репутация отправителя для доменов `.ru`/Mail.ru/Яндекс — письма реально доходят, а не падают в спам |
| SendPulse | Сопоставимая цена, есть бесплатный лимит на старте | Чуть более современный API, но ориентирован больше на маркетинговые рассылки | Тоже работает с РФ-аудиторией, но репутация отправителя под транзакционные письма не настолько обкатана именно на этом сценарии |
| Mailganer | Похожая цена | Специализируется на доставляемости в мейл-провайдеры РФ | Менее известен → меньше готовых примеров, меньше людей, столкнувшихся с теми же граблями |

**Выбор (ИСТОРИЯ до 2026-09-16): Unisender Go** — выбор Unisender в целом уже зафиксирован в [[05-стек]] (раздел 8); здесь уточнение — берём именно его транзакционный продукт (не полную платформу с рассылками), потому что продукту нужно ровно одно: письмо подтверждения и письмо сброса пароля долетают до Mail.ru и Яндекс.Почты. Это не зона для экспериментов: письмо либо доходит, либо нет, а более «модный» API ничего не выигрывает там, где решает только репутация отправителя.

**🔴 ПЕРЕСМОТРЕНО 2026-09-16: основной канал — SMTP через уже оплаченный ящик `support@whygrid.app` (VK WorkSpace), Unisender Go — запасной.** Причина пересмотра: реальный объём писем оказался **~15/мес** (30 писем за первые 2 месяца) при тарифе Unisender «Стартовый 6K» — 800₽/мес за 6000 писем. Абонентка не оправдана таким объёмом, а почтовый ящик уже оплачен для нужд поддержки — платить дважды за практически неиспользуемую ёмкость не за что. Домен `whygrid.app` уже был технически подтверждён под mail.ru-инфраструктуру (SPF/DKIM в DNS ради самого ящика поддержки, см. историю ящика в разделе 2.2 ниже) — доставляемость не пострадала.

**Важное протокольное ограничение (обнаружено вживую 2026-09-16):** SMTP-сервер mail.ru требует, чтобы адрес «от кого» (`MAIL FROM`) буквально совпадал с логином SMTP-аутентификации — иначе `501 sender address must match authenticated user`. Технический логин ящика `support@whygrid.app` в mail.ru-инфраструктуре — `whygrid.app@mail.ru` (тот же ящик, два адреса), поэтому все автоматические письма продукта показывают отправителя `whygrid.app@mail.ru`, а не `support@whygrid.app`. Сам адрес `support@whygrid.app` остаётся публичным адресом поддержки (в оферте, на странице поддержки, для переписки из веб-интерфейса — там это ограничение не действует, оно только у прямого SMTP-протокола).

**Адаптер:** `adapters/email/smtp/` (nodemailer) — основной; `adapters/email/unisender/` остаётся в дереве как запасной путь (правило 4), переключение — одна переменная окружения, без нового деплоя. Запасной вариант следующего уровня — SendPulse (новый файл адаптера при необходимости).

**При недоступности:**
- Письмо подтверждения / сброса пароля не уходит → стандартный путь очереди (повтор с задержкой → карантин при исчерпании попыток, как и остальная фоновая работа в [[04-потоки-данных]], раздел 3); пользователь не блокируется — может запросить письмо повторно;
- Это не критическая поломка продукта (аккаунт можно создать и без подтверждения, подтверждение требуется до первой оплаты) — задержка в письмах не останавливает основной сценарий.

**Дневной денежный потолок:** не более **300 писем в сутки**. При ожидаемой нагрузке — несколько сотен пользователей, по 1–2 письма на регистрацию и редкие сбросы пароля — это кратный запас над нормой; в деньгах при тарифах транзакционной рассылки это первые рубли в сутки. Смысл потолка — не контроль обычного расхода (он и так копеечный), а защита от аномалии: например, бага в фоне, который начнёт слать письма по кругу.

### 2.2. Уведомления администратору — реактивные алерты и ежедневный дайджест

Telegram-бот выполняет две разные функции: **реактивные алерты** (сразу, когда что-то пошло не так) и **плановый дайджест** (утром каждый день — сводка состояния продукта за сутки).

**Реактивные алерты** — в [[04-потоки-данных]] прямо описаны события, требующие немедленной реакции: задача ушла в карантин (событие №15), сработал авто-стоп по расходам на Claude (раздел 5, шаг 3), задача висит в очереди дольше нормы (шаг 1). Это сигнал «зайди и посмотри прямо сейчас».

**Ежедневный дайджест** — cron-задача в 9:00, запрос к собственной базе и Anthropic API, одно сообщение в Telegram. Состав дайджеста:

| Блок | Что показывает | Сигнал к действию |
|---|---|---|
| **Пользователи** | Новые регистрации за сутки / загружено турниров / активных диалогов | Если всё нули несколько дней подряд — смотреть воронку |
| **Расходы Claude** | Потрачено за сутки ($X из $30) / остаток баланса на Anthropic Console | Если расход стабильно > $25 — пересматривать лимит или тарифы |
| **Подписки** | Всего активных / новые за сутки / отменённые за сутки | Churn выше новых — сигнал смотреть retention |
| **Очередь** | Задач ждут / задач в карантине / среднее время обработки за сутки | Очередь не разгребается > 15 мин стабильно → сигнал апгрейда сервера |
| **Инфраструктура** | CPU % / RAM % / место на диске (HH-файлы) | CPU > 70% или диск > 80% → пора апгрейдить или чистить |

**Сигнал масштабирования сервера** — не отдельный алерт, а вывод из дайджеста: если несколько дней подряд очередь не разгребается в норму или CPU стабильно выше 70%, в дайджесте появляется строка «⚠️ Пора смотреть апгрейд». Это осознанный выбор — реже ложные срабатывания, чем при пороговом алерте по одному дню.

В [[04-потоки-данных]] прямо описаны события, требующие немедленной реакции одного человека — автора продукта: задача ушла в карантин (событие №15), сработал авто-стоп по расходам на Claude (раздел 5, шаг 3), задача висит в очереди дольше нормы (шаг 1). Это не письма пользователю — это сигнал «зайди и посмотри», и здесь критична скорость доставки, а не репутация почтового домена.

| Вариант | Цена | Простота подключения | Надёжность/скорость для одного человека |
|---|---|---|---|
| **Telegram-бот (Bot API)** | Бесплатно | Один токен, один HTTP-запрос на отправку сообщения — никакой интеграции со сторонним SaaS | Push-уведомление на телефон за секунды; автор продукта уже использует Telegram ежедневно — сообщение увидит сразу, а не «через час, когда откроет почту» |
| Email самому себе (через тот же Unisender) | Бесплатно/копейки | Тот же адаптер, что и для писем игроку — формально «ничего нового» | Почта — не канал немедленной реакции; алерт о карантине, прочитанный через 6 часов, обесценивает саму идею алерта |
| Slack / отдельный канал мониторинга | Бесплатно на старте, платно при росте | Требует завести аккаунт сервиса, который иначе продукту не нужен — лишняя сущность ради одного канала уведомлений | Удобно для команды; для одного человека — просто ещё один мессенджер поверх уже используемого Telegram |

**Выбор:** **Telegram-бот**. Это не «третий поставщик ради третьего» — это бесплатный канал, который уже есть и уже используется автором продукта каждый день, и который доставляет сообщение быстрее любого email. Для алерта «задача ушла в карантин» или «сработал дневной авто-стоп по Claude» скорость реакции — это и есть весь смысл уведомления; email здесь предсказуемо проигрывает.

**Адаптер:** `adapters/notify/telegram/`, порт «сообщи администратору о событии». Запасной вариант — переиспользовать `adapters/email/` (тот же Unisender) для второго канала, если Telegram станет недоступен в какой-то момент — без переписывания бизнес-логики, просто второй адаптер за тем же портом.

**При недоступности Telegram:** алерт не теряется — событие (карантин задачи, превышение потолка) в любом случае фиксируется в базе (статус `poisoned`, запись о срабатывании авто-стопа), уведомление — это вторичный канал поверх уже сохранённого факта; при следующем заходе в админку администратор увидит то же самое. Резервный канал — email на тот же адрес через `adapters/email/`.

**Дневной денежный потолок:** сервис бесплатный — потолок ставить не на что. Содержательный «потолок» здесь другой — частота уведомлений: если в сутки приходит больше N алертов одного типа (например, повторяющийся карантин одной и той же задачи), есть смысл схлопывать их в одно сообщение «эта задача упала уже 5 раз», чтобы не утопить администратора в потоке однотипных сигналов. Это деталь реализации адаптера, не денежный лимит.

## 3. Хранение файлов (HH-файлы)

Уже решено в [[03-база-данных]] и подтверждено в [[05-стек]] (раздел 4) — здесь фиксирую операционные детали, которых требует эта задача.

### Сравнение вариантов

| Вариант | Цена | Простота подключения | Надёжность |
|---|---|---|---|
| **Yandex Object Storage** | Копейки при ожидаемом объёме (HH-файл — это текстовый файл на десятки–сотни КБ, тысячи файлов в месяц — это рубли) | S3-совместимый API — любая стандартная S3-библиотека для Node.js работает без переделки; тот же провайдер, что хостинг и БД — единый биллинг и доступ | Зрелый сервис того же облака, что уже выбрано под остальное — один периметр безопасности вместо двух |
| Selectel S3 | Чуть дешевле | Тоже S3-совместимый — переключение тривиально | Тоже надёжен, но второй провайдер вместо одного — лишняя точка интеграции без выигрыша при уже выбранном Yandex Cloud |
| VK Cloud (бывш. Mail.ru Cloud) Object Storage | Сопоставимая цена | Тоже S3-совместимый | Тоже зрелый, но то же соображение — третий провайдер ради третьего, когда один уже закрывает всё нужное |

### Выбор

**Yandex Object Storage** — обоснование подробно изложено в [[05-стек]] (раздел 4): HH-файлы — самые чувствительные личные данные продукта (никнеймы, риск №5 из [[00-правила-проекта]]), хранить их у того же провайдера, что и базу, означает один периметр безопасности вместо двух, и закрывает требование 152-ФЗ ([[05-стек]], раздел 0) без компромиссов.

**Адаптер:** `adapters/storage/yandex-s3/`, порт «сохрани файл и отдай его обратно по ключу». Запасной вариант — Selectel S3, переключение тривиально (S3-совместимый API).

**При недоступности:**
- Загрузка HH-файла падает на этапе сохранения в хранилище → пользователь видит понятную ошибку «не удалось сохранить файл, попробуйте ещё раз», запись о турнире не создаётся (тот же принцип, что и для обрыва сети при загрузке — [[04-потоки-данных]], раздел 2, событие №2: мусора не остаётся, повтор — рукой пользователя);
- Уже сохранённые файлы недоступны для чтения → плановая ночная чистка (`PURGE_HH_FILES`) откладывается на следующий цикл — это не критично, она и так не строго привязана ко времени ([[04-потоки-данных]], раздел 2, событие №10).

**Дневной денежный потолок:** не более **10 ₽/сутки**. При ожидаемом объёме (десятки HH-файлов в сутки по сотни КБ) реальный расход — копейки; этот потолок не контролирует нормальную нагрузку, а служит сигналом аномалии — например, бага в фоновой задаче, который начнёт писать файлы по кругу или сохранять файлы аномального размера.

## 4. Статистика

Здесь нужно разделить две разные вещи, которые часто путают под одним словом «статистика»: **бизнес-метрики продукта** (понять, доходит ли продукт до людей) и **технический мониторинг ошибок** (понять, что сломалось).

### 4.1. Бизнес/продуктовая аналитика — нужна

«Три числа», которые автор смотрит каждый день ([[05-стек]], раздел 9 — регистрации, активные подписки, доля турниров до готовой карточки), уже считаются прямыми запросами к собственной базе и не требуют внешнего сервиса. Но эти три числа не показывают то, что происходит **до** регистрации: сколько людей вообще зашло на сайт, на каком шаге воронки «зашёл → зарегистрировался → оплатил» теряются. Для одного человека, который должен понимать, доходит ли продукт до рынка, это не «красивая визуализация», а прямой ответ на вопрос «вообще ли кто-то находит продукт».

| Вариант | Цена | Простота подключения | Надёжность/соответствие аудитории |
|---|---|---|---|
| **Яндекс.Метрика** | Бесплатно | Один скрипт на страницу, готовая интеграция с Next.js, визуальная карта воронки «из коробки» | Стандарт рынка для рунета, данные физически в РФ — не создаёт нового вопроса по 152-ФЗ (в отличие от Google Analytics) |
| Google Analytics | Бесплатно | Тоже один скрипт, привычнее части западных гайдов | Передаёт данные за рубеж — то же самое соображение раздела 0 в [[05-стек]], которое уже исключило Stripe/AWS, действует и здесь: создаёт лишний вопрос по трансграничной передаче ради сервиса, у которого есть бесплатный РФ-аналог без этой проблемы |
| Top.Mail.ru (VK) | Бесплатно | Тоже простой скрипт | Тоже РФ-сервис, но у Яндекс.Метрики шире распространение и больше готовых примеров именно под SaaS-воронки |

**Выбор: Яндекс.Метрика.** Бесплатно, данные в РФ (не создаёт нового вопроса по 152-ФЗ, который раздел 0 в [[05-стек]] уже решил для остальных сервисов в пользу российских поставщиков), и закрывает ровно ту дыру, которую не закрывают «три числа» из БД — воронку до регистрации. Здесь не нужен адаптер в смысле правила 4: это не сервис, через который ядро продукта вызывает бизнес-операцию, а внешний скрипт аналитики на стороне фронтенда — подключается и отключается независимо от бизнес-логики.

**При недоступности:** ничего не ломается — это сервис веб-аналитики, не часть критического пути; временная потеря данных за день не требует реакции.

**Дневной денежный потолок:** сервис бесплатен при любом реалистичном для этого продукта объёме трафика — потолок ставить не на что.

### 4.2. Мониторинг ошибок (Sentry и аналоги) — отдельный сервис не нужен

Часто в эту же категорию «статистика» включают системы вроде Sentry — сбор и группировку ошибок приложения. Здесь сознательно не беру отдельный сервис под это:

- Yandex Cloud, уже выбранный как основное облако ([[05-стек]], раздел 3), включает Cloud Logging и Cloud Monitoring — сбор логов и базовые алерты по ошибкам уже доступны в рамках уже оплаченной инфраструктуры, без подключения нового вендора;
- Sentry как SaaS — иностранный сервис: в текст ошибки может попасть что угодно, включая фрагменты пользовательских данных (например, никнейм из необработанного исключения парсера) — это создаёт ровно тот же вопрос трансграничной передачи персональных данных, который раздел 0 в [[05-стек]] уже решил в пользу российских поставщиков; самостоятельный хостинг Sentry — это инфраструктура, которую «нужно поднимать, оплачивать и мониторить, не давая ничего такого, чего не даёт уже выбранный Yandex Cloud» (та же логика, что в [[05-стек]] разделе 5 про очередь задач);
- Карантин задач и превышение дневного потолка LLM — главные сигналы «что-то не так» для этого продукта — уже обрабатываются собственным механизмом очереди ([[04-потоки-данных]], раздел 3) и уходят администратору через Telegram-бота (раздел 2.2 выше). Дополнительный сервис добавил бы второй канал уведомлений об одном и том же без новой ценности.

Если объём ошибок вырастет настолько, что встроенного логирования Yandex Cloud перестанет хватать — это решается позже через адаптер, без пересмотра архитектуры (правило 4).

## 5. Генерация моделей (текст / картинки / голос / видео)

Выбор модели для генерации **текста** уже сделан и подробно обоснован в [[05-стек]] (раздел 6) — это «жетон №1» продукта: **Claude Sonnet 4.6** для всех платных задач очереди (`GENERATE_HAND_ANALYSIS`, `GENERATE_VERDICT`, `GENERATE_CHAT_REPLY`), запасной вариант Claude Haiku 4.5 для самых простых задач через конфиг. Здесь не повторяю это сравнение — только операционная часть, которой требует эта задача:

**Картинки, голос, видео — продукту не нужны.** Сократовский диалог — это текст (вопрос → ответ игрока → текстовый разбор), карточка турнира — это числа и текст. Ни одна часть MVP ([[01-что-строим]]) не предполагает визуального, голосового или видеоконтента, сгенерированного моделью — добавлять сюда ещё одного поставщика значило бы тратить второй и третий «жетон на эксперимент» там, где в этом нет необходимости ([[05-стек]], раздел 10, последний пункт списка «что сознательно не выбрал»).

**Адаптер:** уже зафиксирован — `adapters/llm/`, порт «сгенерируй разбор раздачи / ответь на вопрос игрока» ([[05-стек]], раздел 11).

**При недоступности Claude API:** уже подробно описано в [[04-потоки-данных]] — стандартный путь очереди (повтор с задержкой 1/5/30 минут → карантин конкретной раздачи, не всего турнира — раздел 5, шаг 3); карточка открывается, как только обработаны все ~10 раздач, успехом или карантином — единичный сбой не блокирует показ остальных (тот же документ, шаг 4).

**Дневной денежный потолок:** в [[04-потоки-данных]] (раздел 5, «Дневной потолок расходов и авто-стоп») уже зафиксирован принцип — порог оценивается из экономики MVP и хранится в конфиге, при превышении новые платные задачи перестают забираться из очереди, администратору уходит уведомление (через Telegram-бота, раздел 2.2 выше). Конкретное число, которое стоит туда заложить:

> Из расчёта [[../idea/mvp]] (~$0.05–0.07 за турнир, до 500 пользователей с лимитом 20 турниров/мес) — пиковая нагрузка: 500 × 20 ÷ 30 ≈ 333 турнира в сутки × $0.07 ≈ **$23 в сутки** на пике. Предлагаемый потолок по этому сервису — **$30 в сутки** — даёт запас над расчётным пиком и одновременно служит ранним сигналом: если расход стабильно подбирается к этой границе, это значит, что продукт растёт быстрее заложенного прогноза, и стоит пересмотреть число, а не просто поднимать потолок.

Это — потолок конкретно по Claude API; как он соотносится с общим дневным лимитом продукта и автоматическим стопом всего биллинга — фиксируется отдельно в `07-безопасность.md`.

## 6. MCP — инструменты для Claude во время разработки

MCP здесь — не часть продукта (пользователь их не увидит), а инструменты, которые ускоряют именно разработку этого продукта одним человеком при помощи Claude Code. Беру только то, что отвечает на конкретную потребность этого проекта:

- **PostgreSQL MCP** — прямой доступ на чтение к рабочей/тестовой базе. Схема продукта — это очередь задач, машина состояний турнира, журнал платежей ([[03-база-данных]]); во время разработки и отладки регулярно нужно посмотреть «а в каком статусе сейчас эта задача» или «что реально записал парсер» — без этого MCP пришлось бы каждый раз писать одноразовые скрипты или переключаться в отдельный клиент СУБД.
- **Playwright MCP** — провести браузер по живому приложению. CLAUDE.md проекта прямо требует «для UI-изменений — пройти golden path в браузере, а не полагаться на типы и тесты» (это из общих правил работы); путь «загрузил HH-файл → дождался разбора → открыл карточку → ответил на сократовский вопрос» — это ровно тот сквозной сценарий, который стоит проверять руками Claude в браузере, а не только юнит-тестами парсера.
- **Fetch / HTTP MCP** — проверка вебхуков ЮKassa и поведения адаптеров на реальных HTTP-вызовах при отладке интеграций (раздел 1 и 5 этого документа) — позволяет воспроизвести входящий вебхук или вызов внешнего API без выхода из сессии с Claude.

Сознательно не беру: GitHub MCP (для одного разработчика обычный `git`/`gh` через терминал не создаёт трения, которое стоило бы решать отдельным MCP), Sentry MCP (сервис не выбран — раздел 4.2), Stripe MCP (продукт работает с ЮKassa, не Stripe — официального MCP под ЮKassa на сегодня нет, и плодить кастомный ради разработки не оправдано).
